## 1. Purpose and scope

- **Need:** a reusable site footer organism in `@egdev/ui`, with a motto, identity and tagline, a section navigation group, social destinations and legal content. It is a region, not a page. All content, destinations, logo artwork and language are consumer supplied; no Pulso names, copy, links, accounts or year are defaults.
- **Non-goals:** no 3D, particles, large CTA, page layout or router, fetching, analytics, sticky behavior, intersection observer, SectionNav visibility or scroll choreography. The host coordinates the latter; the footer remains passive except for supplied native links.
- **Cataloging:** new `Footer` organism at `packages/ui/src/organisms/footer/`, catalog row `scripts/catalog_data.py:102`: Logo + SocialLinks + Link, no Radix base. Reuse alone fails because Logo, SocialLinks and Link each own one part, not the site-wide hierarchy. A variant of any would add a different structural responsibility. App composition works once, but repeats the same layout and landmark in new web views; the approved web-consumer amendment permits a generic organism. No hidden site footer to extract. Classification is based on region and coordinated parts, not size. The catalog decision does not approve this API.
- **Inspected public working-tree evidence:** `packages/ui/src/index.ts` exports Logo, SocialLinks, Link and Text/Heading and no Footer; individual availability is verified from source, irrespective of older broad availability claims in shared policy. `packages/ui/src/atoms/logo/types.ts` (`LogoProps`, SHA-256 `c94a94db17133bd7b28dcd8763fdf00f40fb788379f2074432599c68c5a1ba31`) exposes wordmark/mark, lg and named native link, but no router `asChild`; a consumer may instead supply another accessible brand element. `packages/ui/src/molecules/social-links/types.ts` (`SocialLinksProps`, `SocialLinkItem`, SHA-256 `dafd4d7a0ec76696e85d2ad1856998720c6a68ceb5f805c0a584c59ae7bef417`) supplies named profile links, required stable IDs, decorative icons, HTTPS validation, opt-in external and `caption={null}`. `packages/ui/src/atoms/link/types.ts` (`LinkProps`, SHA-256 `b5e5ba0b47c7e53c9a3759888c1d746a82596537fd3834d1ca3dd2a4b05503f3`) supplies a native/Slot anchor, optional arrow and brand ink; its appearance differs from the source's secondary-to-white links. `packages/ui/src/primitives/text/types.ts` (`TextProps`, `HeadingProps`, SHA-256 `badce40976a01fb4c0079a1481c5ba2fcdf88c10dd2bee6556244991fdfd21c9`) supplies non-heading display text and trailing accent with explicit canvas/raised context.

## 2. Anatomy and composition

The following compound API is a **recommendation**, subject to OQ-1 and OQ-2. All five named parts are optional, each used at most once in the order shown. Absence removes its wrapper; no placeholder or domain data is created.

| Part | Responsibility | Element and content |
| --- | --- | --- |
| `Footer` | Site-level boundary | native `footer`, containing the parts in source order |
| `FooterMotto` | Display phrase and accent | consumer-supplied non-interactive `Text` element; native paragraph, not a required heading |
| `FooterBrand` | Brand identity and tagline | consumer-supplied Logo or other named brand link and optional descriptive copy; no nested anchors |
| `FooterNavigation` | One named section-link column | native `nav` named by its visible native heading and a `ul` of consumer-defined anchors |
| `FooterSocial` | Social column | consumer supplies its heading and one configured `SocialLinks`; no additional unnamed navigation landmark |
| `FooterLegal` | Lower legal/credit row | consumer-supplied non-interactive text or links in reading order |

Root preserves `eg-footer` as a stable public marker. Proposed part markers `eg-footer__stage`, `__grid`, `__legal` are stable only if approved; names without prefix in this sentence expand to `eg-footer` + suffix. Other legacy markers are not automatically public override APIs. No existing legacy consumer is changed. No new Radix primitive: native landmarks, lists and anchors have native keyboard semantics; a supplied `Link` retains its own Slot implementation. No invented keyboard model.

## 3. Public API

| Prop / part | Type | Required | Default / rule |
| --- | --- | --- | --- |
| `Footer.children` | `ReactNode` | yes | Named parts in the documented order, each at most once; no implicit content |
| `FooterMotto.children` | `ReactElement` | yes | One non-interactive consumer `Text` display element; consumer owns accent and context |
| `FooterBrand.children` | `ReactNode` | yes | Consumer brand element and optional tagline; consumer ensures one accessible name and no nested links |
| `FooterNavigation.label` | `string` | yes | Non-empty visible heading and accessible name of the nav; no fallback wording |
| `FooterNavigation.level` | `2 \| 3 \| 4 \| 5 \| 6` | no | `2`, consumer selects outline-appropriate rank |
| `FooterNavigation.items` | `{ href: string; label: string }[]` | yes | Ordered section destinations; empty array omits the entire navigation; item labels and destinations are consumer data |
| `FooterSocial.children` | `ReactNode` | yes | Consumer heading and named `SocialLinks`; pass explicit `label` and `caption={null}` to avoid default English text |
| `FooterLegal.children` | `ReactNode` | yes | Consumer-supplied legal text and optional links; wraps naturally |
| root / part `className` | `string` | no | Outer placement, margin and sizing only; no appearance or internal layout override |

Navigation entries require non-empty `href` and non-blank `label`; invalid entries are omitted without rendering an unnamed link, and if none remain the group is omitted. Order is preserved. Do not alter, deduplicate, infer, open a new tab, or rewrite supplied URLs. Native links navigate on Enter; handlers and router interception remain with the host. If router-controlled links are required instead of the simple data schema, choose the supplied-link alternative in OQ-1; this draft does not promise both. SocialLinks retains its own HTTPS, duplicate-ID, invalid-entry and new-tab rules; Footer does not duplicate those rules. A host must avoid an empty social heading if SocialLinks omits all invalid items.

**Prop naming lookup:** [registry](../../../../skills/_shared/prop-naming.json) and [generated view](../../../prop-naming.md) checked by meaning, name and aliases. Proposed own `FooterNavigation.items` → approved `collection-items`; `label` → `accessible-name`; `level` → `heading-level`. Item `href` is native destination and item `label` is the accessible link name → `accessible-name`. `children` and `className` are React/native composition, not new own naming conventions. No proposed `footer` prop: approved `panel-footer` explicitly excludes site footers. `product-identity` would describe a structured product object, but the brand is a slot; `trailing-text-accent` and `accent-line-break` apply to the supplied Text, not new Footer props. `choice-options` excludes navigation; `trailing-actions` excludes primary navigation. No new registry entry or exception is proposed. New Footer usages require future review of `FooterNavigationProps` and its actual whole-file source hash when that file exists; no revision or convention approval is invented. The observed SocialLinks and Text source hashes are above.

**Native attributes:** proposed root forwards compatible `ComponentPropsWithoutRef<'footer'>` including `id`, `data-*`, and optional accessible name, except `children`, `dangerouslySetInnerHTML`, `role`, `style` and `tabIndex`; root `className` via `cn()`. No ref or `asChild`. Parts own their corresponding children and compatible attributes; no hidden per-part appearance surface. No controlled/uncontrolled state. New named exports and types are proposed only; React 18/19 packed-consumer evidence is a future plan gate.

## 4. Behavior

| Given / action | Expected result | Event |
| --- | --- | --- |
| Parts supplied | Motto, identity, navigation, social and legal appear in supplied documented order, with no Pulso content injected | none |
| Optional part absent | Its region and empty wrapper are absent | none |
| Navigation has no valid entries or blank label | Navigation and its heading are omitted; no unnamed landmark | none |
| Navigation entry activated | Native link follows its supplied destination; no interception or automatic new tab | native event only |
| Social entries invalid or empty | Delegated SocialLinks behavior; consumer avoids an orphaned social heading | none |
| Viewport at most 860px | Recommended two-column layout with brand spanning both, subject to OQ-3; above 860px three columns | none |
| Long labels, legal text or narrow width | Text wraps; no clipping or visual reordering; social icons wrap under their own contract | none |
| Footer enters viewport | Footer itself takes no action; host may coordinate SectionNav | none |

No own selection, loading, disabled, state attributes, observer or announcements. Social controls retain their own hover, focus, target-size and reduced-motion behavior. No automatic heading-level or backdrop detection.

## 5. Accessibility

A native `footer` has the implicit `contentinfo` landmark only when not descended from a sectioning-content element or `main`; hosts place the site footer outside `main` and other sectioning contexts. A nested footer is not promised a site landmark. `FooterNavigation` names the `nav` with `aria-labelledby` pointing to its visible heading via per-instance `useId()`; the heading's selected rank must fit the host outline. SocialLinks renders a named list, not a navigation landmark, and each supplied icon link has its own accessible name. Consumer social heading must remain associated by its own semantic context; no duplicate or unnamed landmark is invented. The brand link is named once, and decorative SVGs remain hidden by their owners. No click handlers or tab stops on the footer itself. Native Tab/Enter, visible focus and accessible new-tab notices belong to each link; plan must test keyboard order and at least 44px touch targets, including section links, without assuming their current atom ensures that. No live announcement is needed. Test multiple instances for unique IDs, landmark placement and names.

## 6. Appearance

- **Register / Material, OQ-4:** recommend a calm Grafito reading-register footer, separate from the preceding Closing scene; ask for an explicit token-backed, non-flat Footer boundary/surface recipe before implementation. The source shows canvas black with red top rule and subtle separators. `docs/MATERIAL.md` describes the footer among the faded edges of a grey reading group; it does not authorize using Gauge's transparent-frame exception, cloning Surface classes, an arbitrary handwritten gradient or a generic raised card. Whether the host's SectionShell owns background/fade and Footer owns a top boundary is an explicit owner choice. Surface is not assumed available as a current compliant prerequisite merely because older specs mention it. No token or dependency change is approved.
- **Typography / link discrepancy:** consumer-supplied `Text` may express the non-heading motto and trailing accent; actual canvas or raised tone follows the approved host recipe. The source shows secondary section links turning white on hover, whereas `Link` currently uses brand ink and optional arrow. Do not silently override Link appearance through `className` or claim parity: select system Link (`arrow={false}`) with its documented appearance, or approve a separate compliant footer-link recipe/atom change in OQ-5. SocialLinks `variant="ghost"`, `size="lg"`, `caption={null}`, explicitly supplied list label and consumer icons is a candidate close to the source while preserving 48px targets; verify actual rendered contrast, gap and focus. The host supplies the SocialLinks heading and item data.
- **Responsive geometry, OQ-3:** source `packages/ui/src/styles/legacy/bundle.css:687–698` uses `1.4fr 1fr 1fr`, switching at inclusive `max-width:860px` to two equal tracks with first child spanning. `--breakpoint-section-header-split: 860px` is a specifically named SectionHeader token (`packages/tokens/src/theme.css:12–13`), not evidence of general Footer approval. The CommunityCard owner amendment authorizes `min-[48rem]:` only for that component and says the default `md` breakpoint is absent. Recommend a separately owner-authorized Footer-local static **`max-[860px]:`** variant, inclusive at 860px, not `md:` and not reuse of the unrelated token; verify emitted CSS and 859/860/861px browser geometry. No token change. If owner prefers a shared token, its scope and addition need separate approval.
- **Legacy collision:** the retained legacy `eg-footer` root and `eg-footer__stage`, `__grid`, `__legal` rules (bundle.css:677–698) apply position, border, padding, max-width, grid, typography, spacing and inclusive media rules. Even a marker-only root inherits unlayered/legacy declarations unless the actual cascade is verified. A future plan must enumerate each emitted legacy selector/property for all retained markers, explicitly neutralize or match each using scoped token-backed static utilities at the applicable viewport and state, and verify computed styles with legacy CSS loaded at both breakpoint sides; preserve old CSS and other consumers. Never assume `cn()`/class-string ordering beats selector specificity or layers. Other reused components retain their own legacy neutralization contracts. The nested `.eg-footer__motto .eg-title__accent` selector is another collision if those markers are used together.
- **Composition and files:** CVA in `types.ts` and `cn()` per supported part, static token-backed utilities only; class merging handles recognized conflicts, not all selectors or variants. No inline appearance or dynamic geometry. Planned six meaningful files: `types.ts` (props and recipes), `useFooter.ts` (normalization, per-part classes and IDs), `Footer.tsx` (JSX), `Footer.test.tsx`, `Footer.stories.tsx`, `index.ts`. **No stylesheet** is the current recommendation, conditional on an approved recipe and effective local neutralization; if utilities cannot do this, a meaningful bounded stylesheet role requires separate spec/plan approval, never a dummy. No extra internal modules proposed.

## Blocking owner questions

1. **Anatomy and inputs:** compound slots for motto, brand, social and legal plus structured navigation, or fully structured props / fully consumer-rendered links? **Recommend the compound shape above:** it accepts accessible brand/router and localized content, while a labelled data-driven navigation avoids repetition. Foundation `Footer/README.md:1–26`, `preview.html:15`, and `scripts/catalog_data.py:102` show the complete region and the existing composition. No Pulso defaults.
2. **Landmarks and labels:** require site placement outside `main`, native footer and a visibly headed named nav, while SocialLinks remains a separately named list? **Recommend yes**; do not force `role=contentinfo` inside `main` or nest landmarks solely for styling. `reference-web/pulso-source.html:1192–1229`; `packages/ui/src/molecules/social-links/SocialLinks.tsx` and `types.ts` describe the list.
3. **Breakpoint:** approve a Footer-only `max-[860px]:` inclusive split, reuse the SectionHeader-specific token, or choose a separately approved shared token? **Recommend the local 860px variant**, matching the source without widening the SectionHeader token or the CommunityCard-only 48rem grant. Evidence: `packages/ui/src/styles/legacy/bundle.css:687–698`, `packages/tokens/src/theme.css:12–13`, `docs/components/community-card/v0.1/responsive-breakpoint-amendment.md:3–7`.
4. **Material / register:** approve a calm Grafito footer with host-owned SectionShell surface/fade and an independently approved Footer boundary recipe, or specify another compliant material treatment? **Recommend host-owned reading-register background/fade and separately approved token-backed boundary**, not an assumed transparent-frame exception. `docs/MATERIAL.md` Principles, Recipes and En la web; source Footer README usage.
5. **Link appearance:** retain existing system Link's brand ink with `arrow={false}`, or commission an explicitly approved secondary-to-white link treatment matching the source? **Recommend retain Link for v0.1 and record the visual deviation**, unless visual fidelity is required enough to justify a separate Link contract. Evidence `packages/ui/src/atoms/link/types.ts` `linkVariants`; `packages/ui/src/styles/legacy/bundle.css:690–692`.
6. **SectionNav visibility:** should the host, not Footer, observe the footer and control SectionNav? **Recommend host ownership**, with no callback or observer in Footer. Foundation `Footer/README.md:29–31`; `reference-web/pulso-source.html:1367–1393` places footer in page choreography.
