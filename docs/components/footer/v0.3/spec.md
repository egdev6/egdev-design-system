## 1. Purpose and scope

- **Need / non-goals:** egdev.es marks the current page with `aria-current="page"` in TopBar and in the mobile NavList, but cannot do it in `FooterNavigation`: `FooterNavigationItem` is only `{ href, label }` and the component renders the anchors itself (ODD S4, #559). The footer links must expose the current page the same way, with the host marking at most one. Non-goals: no visible current-page treatment (OQ-1); no automatic detection from URL, router, scroll position or order; no marking of consumer-supplied brand, social or legal links; no new part, no new prop on `Footer` or `FooterNavigation`, no shared type, token, dependency or stylesheet; no change to `Link`, TopBar, NavList or any other component; no `onNavigate` or router composition (links stay native and the host owns interception, as in v0.2).
- **Cataloging decision / alternatives:** **Variant, specifically an API variant and not an appearance variant** (approved, ODD L3): `FooterNavigationItem` gains the optional `'aria-current'?: 'page'`, following the TopBarItem contract; Radix base none. Options that precede it and were rejected: *reuse unchanged* fails because the anchors are rendered inside `FooterNavigation` from `{ href, label }`, so a consumer has no way to set the attribute (`packages/ui/src/organisms/footer/Footer.tsx:62-70`; the issue records no mitigation). *Compose* (host-rendered links in a free-form part, `asChild` or a render prop) would lose, per host, the heading-named landmark, the entry validation and the 44.8px target recipe that `FooterNavigation` provides and v0.1 deliberately made data-driven (v0.1 OQ-1). *Extract or new* have nothing to extract or create: the field already exists, by meaning, on sibling components, and a shared helper type would add an abstraction across five components for one optional field.
- **Evidence / level and package:** Organism in `@egdev/ui`, unchanged (`packages/ui/src/organisms/footer/`). Availability comes from the React source and the public barrel, not from CSS, catalog or stories: `packages/ui/src/index.ts:138-156` exports `Footer`, `FooterBrand`, `FooterLegal`, `FooterMotto`, `FooterNavigation`, `FooterSocial` and the types including `FooterNavigationItem`. Verified current shape: `types.ts:4-16` declares `FooterNavigationItem` as `{ href: string; label: string }`; `useFooter.ts:38-46` keeps an entry only with a nonempty string `href` and a nonblank string `label`; `Footer.tsx:62-70` renders each valid entry through the existing `Link` atom (`arrow={false}`) with the Footer-owned target recipe. Verified precedent for the member:

| Component | Declaration | Forwarded to the anchor | How the host duty is documented |
| --- | --- | --- | --- |
| TopBarItem | `packages/ui/src/organisms/top-bar/types.ts:12-13`, `'aria-current'?: 'page'` | `useTopBar.ts:139` | JSDoc “The host marks at most one current page. @control select” |
| NavListLink | `packages/ui/src/molecules/nav-list/types.ts:62-66`, `'aria-current'?: 'page'` | `useNavList.ts:93` | JSDoc “Native current-page indication. The consumer marks at most one link across the list. @control select” |

TabBarItem (`tab-bar/types.ts:18`, `useTabBar.ts:56`) and ModuleRail links (`module-rail/types.ts:14`, `ModuleRail.tsx:22`) declare and forward it the same way. How the precedent documents, validates and tests it (verified by reading):

- **Documents:** a JSDoc line on the item member with `@control select`; the component specs state the duty in prose (TopBar [v0.2 spec](../../top-bar/v0.2/spec.md) §3 “at most one current page” and §5 “at most one `aria-current="page"`”; NavList [v0.2 implementation](../../nav-list/v0.2/implementation.md): “Consumer-supplied `aria-current="page"`; no matching or auto-expansion”; TabBar [plan](../../tab-bar/v0.1/implementation-plan.md): “no route matching, inferred current item”); each has a `CurrentPage` story (`TopBar.stories.tsx:115-117`, `NavList.stories.tsx:60-66`).
- **Validates:** nothing at runtime. The hooks forward `item['aria-current']` unchanged; the only restriction is the type (`'page'`), and “at most one” is a host duty that is neither counted nor enforced.
- **Tests:** a type negative for `'step'` (`TopBar.test.tsx:18-24`); attribute present on the marked anchor and absent on the other (`TopBar.test.tsx:143-144`, `NavList.test.tsx:35-37`); exactly one marked anchor (`TopBar.test.tsx:160`); the mark moving on re-render with focus kept (`TopBar.test.tsx:250-256`) or cleared on update (`NavList.test.tsx:56-57`).

## 2. Anatomy and composition

| Part | Responsibility | Native element / Radix primitive | Allowed content |
| --- | --- | --- | --- |
| `FooterNavigation` | Named section navigation; unchanged apart from the entry field below | native `nav`, heading, `ul`, `li`; no Radix | Consumer-labelled, ordered entries `{ href, label, 'aria-current'? }` |
| Entry anchor | The link of one valid entry; carries `aria-current="page"` when its entry is marked | `a` rendered by the existing `Link` atom with `arrow={false}`; no Radix | The entry `label` text only |
| `Footer`, `FooterMotto`, `FooterBrand`, `FooterSocial`, `FooterLegal` | Unchanged from v0.2 | Unchanged | Unchanged |

- **Radix / composition:** None, as in v0.2. `Link` is reused unchanged: it spreads native props it does not own onto its anchor (`packages/ui/src/atoms/link/useLink.ts:19-31` and `:50-56`), so `aria-current` reaches the DOM without a `Link` change (verified by reading; FT-11 is the planned observation). No `asChild` on `Footer`, on `FooterNavigation` or on the entry anchor.
- **Public markers:** Unchanged: `eg-footer`, `eg-footer__stage`, `eg-footer__grid`, `eg-footer__legal` and `footer-brand`. No marker is added: the current entry is addressed through the native attribute, its role and its accessible name, and the existing tests assert that `eg-footer__link` and the other legacy part markers stay absent (`Footer.test.tsx:82-84`).

**Naming lookup (proposed usage, verified registry):** [registry](../../../../skills/_shared/prop-naming.json) and [generated reference](../../../prop-naming.md), searched by meaning, name and aliases (current page, current section, current link, active, `aria-current`) across all 184 entries.

- **Reused, unchanged:** approved `collection-items` → `FooterNavigation.items` (the entry shape is component-specific, so a new member changes no convention) and approved `accessible-name` → `FooterNavigationItem.label`. Both are already registered Footer usages.
- **New member `FooterNavigationItem['aria-current']`: no entry reused and no entry proposed.** No entry name, alias, usage type or exception covers a per-entry current-page attribute on TopBar, NavList, TabBar or ModuleRail. Closest candidates, rejected: `active-section-id` (`activeId`, SectionNav: a component-level id naming the current section; Footer entries carry no id and L3 approved a per-entry attribute) and `active-row` (`activeRowId`, Table: data-collection rows, explicitly not navigation). A shared `current-page` convention is a separate proposal (OQ-4); nothing is migrated or mass-registered here. No exception is needed.
- **Reviewed source:** `packages/ui/src/organisms/footer/types.ts`, symbols `FooterNavigationProps` and `FooterNavigationItem`, whole-file `sha256:7a294339ead212d93e618a2345bad6c7c38ea9b90b176f031007772eff107aa1`. Proposed declaration, added after `label` in `FooterNavigationItem` (existing members and their JSDoc are untouched):

```ts
  /**
   * Native current-page indication on this link. The host marks at most one link across the Footer;
   * omitted means no attribute is rendered.
   * @control select
   */
  'aria-current'?: 'page';
```

A valid entry is still one with a nonempty string `href` and a nonblank string `label`; the mark is part of the supplied values of a valid entry and is preserved with them (no deduplication, rewriting or interception, as in v0.2 §3).

- **Native props / refs:** Unchanged. `FooterNavigationItem` is a plain data type: it inherits no native props and exposes no ref. Root and part native props, the protected props (`role`, `tabIndex`, `style`, `dangerouslySetInnerHTML`, ref, `asChild`) and the absence of ref forwarding are as in v0.2 §3.
- **Controlled / uncontrolled:** Not applicable: the current page is host-supplied data; the component holds no state and emits no event.
- **Compatibility:** Additive and optional. Every existing `{ href, label }` entry compiles and renders as before, with no attribute. Exports, markers, `className` surfaces, validity rules and the Footer-owned 44.8px target recipe are unchanged. Typing follows TopBarItem: a value widened to `string` is rejected, so hosts pass the literal `'page'` or a conditional that yields `'page'` or `undefined`. React evidence: the attribute is a plain DOM attribute with no React-19-only API; the shared contract's peer range is `^18.3.1 || ^19.3.0`, and the packed-consumer check on 18.3.1 and 19.3.0 is planned (FT-18), not observed.

## 4. Behavior

| Initial state / action | Expected result | Emitted event |
| --- | --- | --- |
| A valid entry has `'aria-current': 'page'` | Its anchor renders `aria-current="page"`; label, `href`, order and classes are unchanged | None |
| An entry omits the member | Its anchor has no `aria-current` attribute | None |
| No entry is marked | No element in the navigation has `aria-current` (a page with no footer destination is a valid host state) | None |
| The marked entry is invalid (blank label, empty or non-string `href`) | The entry is omitted together with its mark; no remaining entry becomes current; the group is omitted when none remain | None |
| The host re-renders with the mark moved to another valid entry (order and destinations unchanged) | The attribute follows the mark; the previous anchor loses it; focus stays on the element that had it | None |
| The marked link is activated | Native navigation, exactly like any other footer link; Footer neither intercepts nor disables it | Native event only |
| The host marks more than one entry (outside the contract) | Each supplied mark is forwarded as supplied; no error, no warning, no winner (same as TopBar and NavList; see OQ-2) | None |
| Several `FooterNavigation` parts in one Footer | The at-most-one rule spans the whole Footer; Footer does not coordinate groups | None |

- **States / representation:** The native `aria-current` attribute on the anchor is the whole representation. There is no `data-state`, no mirrored class and no visual variant; the class list of a marked anchor equals that of the same anchor unmarked (FT-15).
- **Limits / consumer responsibilities:** The host decides which entry is current and marks at most one per Footer. Footer does not infer a mark from `href`, `location`, router state, scroll position or order. The type admits only `'page'`: tokens such as `'location'` (in-page scroll-spy, SectionNav) are not accepted. Consumer-supplied brand, social and legal links own any `aria-current` of their own; this amendment adds no prop for them. Validation of `href` and `label`, and the omission rules, are unchanged.

## 5. Accessibility

- **Accessible name / roles / relationships:** A marked anchor keeps role `link` and the accessible name from its `label`; `aria-current="page"` adds the current-page state on that link only. The navigation landmark keeps its name from the visible heading through `aria-labelledby` and the per-instance `useId()`. No id, relationship, role or live region is added.
- **Keyboard / focus:** Unchanged and native: Tab, Shift+Tab and Enter on every anchor. A marked link is not disabled, not removed from the tab order and has no `tabindex`; marking moves no focus and adds no roving focus or keyboard model.
- **Announcements / other conditions:** Footer announces nothing. The attribute lets assistive technology expose the state; no screen-reader output is claimed from DOM tests, as in v0.2. No non-color cue is added (OQ-1): a sighted user gets no indication of the current page from the Footer itself, and no color-only state is introduced. Footer-owned navigation links keep the local 44.8 × 44.8px target exception; consumer-supplied links remain consumer-owned.
