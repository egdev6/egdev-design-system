## 1. Gates and boundaries

1. Obtain approval of this plan and the exact future surfaces and commands below. Separately resolve and record the two convention approvals in §6; amendment approval alone is not a convention receipt. The owner's choices already approve `pending` on both roots, AlertDialog's placement pair, the focus-retaining guard, consumer-owned announcements, and the bounded same-host stack. Do not reopen these as competing design options.
2. Reuse the exported molecules, individual Radix Dialog and AlertDialog packages, the existing marker-free Dialog scrim/overlay recipes, Surface and IconButton. A visual variant or an app-only guard cannot supply both portal placement and the owned close lock. No new component, custom modal/focus/keyboard engine, dependency, token, inline appearance, dynamic geometry, Surface-paint cloning, legacy rewrite or general overlay ordering policy is proposed.
3. Preserve both molecules' six meaningful roles: `types.ts`, hook, JSX component, main test, stories and `index.ts`. **No stylesheet; no extra internal module.** Existing focused test files remain meaningful additions. `index.ts` and the root barrel need no new exports; verify their existing public components/types and keep recipes private.
4. A container-scoped layout requires a ready, connected, same-document, positioned, non-scrolling host of definite usable dimensions. Explicit viewport scope may use a ready same-document target for mounting alone without requiring that target to position the overlay; ancestor clipping or fixed-position containing blocks can still constrain it. Close before removing or replacing the target. External stacking, shadow roots, iframes, cross-document and live-target movement are outside the guarantee. Container bounds paint, not Radix's document-wide modality.
5. The nested guarantee is only the *same host and common stacking context*, sheet open first and alert opened later, without consumer competing z-index, occlusion or clipping. If the real browser finds sibling ordering insufficient even there, **stop for a scoped stacking decision**; do not assert an untested z-index, add a token, or change all Dialog defaults.

## 3. API, events and accessibility design

- Mirror Dialog's placement union exactly: `{ container?: null; overlayScope?: 'viewport' } | { container: HTMLElement; overlayScope?: 'viewport' | 'container' }`. Omitted/null host uses body and viewport; a ready host defaults to container; explicit viewport under that host stays viewport-scoped. Invalid untyped `overlayScope='container'` without a host renders neither overlay nor content, never a body fallback. Pass `container` to Radix Portal and the derived scope to the existing overlay recipe; consume both props, with no DOM leakage. Preserve the existing body portal's SSR/client-mount behavior. The scoped overlay is absolute/inset and the viewport overlay fixed/inset; no geometry measurement.
- `pending` defaults to false independently on each root. A context provider may coordinate that root's Content and owned decision/close parts without a DOM wrapper, extra module or cross-root propagation. While true, force that Content's `aria-busy=true`; otherwise pass a consumer's existing `aria-busy` through unchanged, including explicit false or absence. Prop changes do not emit callbacks, and controlled `open=false` or unmount remains possible.
- While pending, cancel the top modal's Radix Escape and, for Dialog, outside-interaction dismissal before it requests `onOpenChange(false)`; AlertDialog continues to ignore outside dismissal. Verify a blocked alert Escape cannot close the underlying sheet. Do not suppress normal dismissals when false.
- Expose `aria-disabled=true` on AlertDialog Cancel/Action and Dialog's built-in close/`DialogClose`; retain focusability and the current focused control, suppress normal click handlers and close requests for pointer, Enter, Space and programmatic click, then restore ordinary behavior when false. Do **not** replace this transient state with native `disabled`, pointer-through styling or a new focus move. Preserve an explicitly disabled control's native/Slot precedence and supported className/ref behavior.
- Radix Slot may run a child's handler before a parent bubbling handler. The existing `packages/ui/src/atoms/button/useButton.ts` demonstrates a capture-phase guard for focus-retaining loading; use its established behavioral pattern where compatible, and verify the real multi-level Radix/Slot composition rather than assuming handler order. Test both outer and compatible child's ordinary `onClick` callbacks. A child must spread props, forward its ref and be button-compatible; arbitrary nested interactive controls and consumer capture/native listeners that act before the guard are explicitly unsupported. If the supported Slot path cannot satisfy the lock, stop instead of changing its contract or synthesizing keyboard events.
- `aria-busy` is not an announcement. The consumer supplies visible localized progress and error copy, and any separately designed announcement outside a subtree whose busy state could defer it. No built-in live region or promised immediate speech. Clear busy before presenting an error that must be announced. Uncontrolled ordinary use remains supported; asynchronous success/close should use controlled state or another consumer-owned lifecycle.
- On the **initiating** Action click, the consumer must synchronously `preventDefault()` or use a synchronous `onOpenChange` ref guard before starting work; React's later pending render cannot cancel Radix's first close request. Guard duplicate starts synchronously too. On success, clear the lock and deliberately close; on failure, clear it and keep a recoverable error visible. The lock does not guard arbitrary children, app shortcuts, external controlled state or unmounts.
- Preserve `aria-modal`, names and title/description relations, Cancel initial focus, focus rings, Surface and approved header behavior. On normal nested close, Radix restores focus to the still-connected, enabled child Trigger in the sheet; parent close restores its own Trigger. Triggerless, removed/disabled Trigger and forced close restoration stay consumer-owned. Real browser and assistive-technology checks are separate gates.
