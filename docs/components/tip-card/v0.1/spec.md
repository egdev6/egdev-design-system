## 1. Purpose and scope

- **Need:** one reusable vertical tip poster in `@egdev/ui` so a new web view can present short technical tips, quick posts or cover cards as a 2:3 visual unit. The poster carries a cover image, an optional category badge and one short technical label. No category word, technical name, image, post copy or destination is built in: everything arrives through props.
- **Non-goals:** not the slider (`TipsSlider` is an approved **composition recipe** of `Carousel` + `TipCard`, not an export); not an editorial photograph (`PhotoFrame` is the media atom and `ArticleFeature` is the article card); not a link or a pressable card (the web poster is not interactive; moving through the collection belongs to the host); no coverflow offsets, rotation, depth or fade, no centered/active glow, no image zoom on hover, no isotype artwork, no copy/share control, no counter or progress bar, no routing, no analytics and no data fetching.
- **Cataloging decision / alternatives:** **new** molecule, per [cataloging-draft.md §4](../../web-catalog/v0.1/cataloging-draft.md) and the `TipCard` row in `docs/CATALOGO.md` (action `mover`, source `TipCard (molécula)`, composes `AspectRatio, Text`). Rejected alternatives: *reuse* (`PhotoFrame` is one passive image with an optional plain caption below the figure and no fixed 2:3 poster promise, no badge and no caption row; `Badge` is one label; `ListItem card` is a general content container with a media thumbnail sized by a token square, not a 2:3 poster); *variant* (adding a badge overlay row and a fixed poster proportion to `PhotoFrame` would change its published promise, and its v0.4 contract explicitly excludes overlay captions and image filters; adding a poster shape to `ListItem card` would change that component's responsibility); *compose* (a `PhotoFrame` + `Badge` + heading spelled out in every new view re-implements the same 2:3 reservation, badge placement and mono label row, which is exactly what the approved web-consumer amendment removes); *extract* (nothing inside an existing component hides a poster unit).
- **Evidence / level and package:** molecule in `@egdev/ui`, proposed `packages/ui/src/molecules/tip-card/`. The level follows the responsibility: coordinated concepts (fixed 2:3 cover, category badge, mono label) that only work as one unit, with no section, navigation or interaction responsibility. Verified public React API inspected in this working tree: `packages/ui/src/index.ts` (whole file, `sha256:f85891be7d1d2ffc6d6788c9a06d87c70466213a227dec2abbd2235d2be6bd24`), `packages/ui/src/primitives/surface/types.ts` (`Surface`, `surfaceVariants`, `sha256:26d0726b5034dceb74e0067c1c0df5108d351e948205bbf22b5e187b92d9c0b6`), `packages/ui/src/atoms/photo-frame/types.ts` (`ratio` numerics, `focalPoint`, required `src`/`alt`, `sha256:aca1d91add7e92b3629233d6bc521b2d07d1e7bf14d86795c3ba23fe6213092e`), `packages/ui/src/primitives/aspect-ratio/types.ts` (`ratio` numeric, `sha256:771b93daa9a3c3548cba5ea6172b0182b32705e6ab7caeaf1b207641669ff1ed`), `packages/ui/src/atoms/badge/types.ts` (`tone`, `variant`, `sha256:81d97cd46835e08a2ed5d846d352642ef9230661b4dcfe04d7e4be921c7d6f3e`), `packages/ui/src/primitives/text/types.ts` (`sha256:badce40976a01fb4c0079a1481c5ba2fcdf88c10dd2bee6556244991fdfd21c9`) and `packages/ui/src/molecules/list-item/types.ts` (`ListItemTitle` precedent for a component-owned heading element, `sha256:df2e05c470c79ad94bef1b06c87d118216ea601ebebe1d8aea6cff8c366cbe76`). `packages/ui/src/molecules/carousel/types.ts` (`sha256:e7bec3354a8aceb305f30e48715014d72c31627d86e8fa7b031d9ae52bd53320`) confirms read-only slide content accepts a passive card and marks the active slide with `aria-current`.

## 2. Anatomy and composition

| Part | Responsibility | Native element / Radix primitive | Allowed content |
| --- | --- | --- | --- |
| `TipCard` root | Poster unit: raised Material frame holding the reserved 2:3 cover and the caption row | `article` composed over the public `surfaceVariants` raised recipe | The cover and then the caption row, in that order |
| Cover (`src`, `alt`, `focalPoint`) | The 2:3 image that carries the post | Public `PhotoFrame` (`figure` > `AspectRatio` > `img`) | Exactly one image; required non-empty `alt` |
| Caption row (`eg-tip-card__cap`) | Row holding the category badge and the technical label below the cover | Internal `div` | The badge and the heading, nothing else |
| Badge (`badge` prop) | Category word of the tip | Existing `Badge` (`tone="brand"`, `variant="solid"`) | One short text run; omitted when not supplied |
| Heading (`title` + `level` prop) | Mono technical label and the card's accessible name | `h2`–`h6` selected by `level` | One plain text run; blank titles warn in development and render nothing |

- **Radix / composition:** no Radix primitive is needed. The poster owns no keyboard model, focus management, selection or dismissal, so no primitive is delegated to and none is invented. The cover reuses the public `PhotoFrame` atom (which already composes `AspectRatio`), the badge reuses the public `Badge` and the frame reuses the public `surfaceVariants` recipe. No `asChild`, no ref and no new dependency.
- **Public markers:** `eg-tip-card` is the stable public root; the caption row keeps `eg-tip-card__cap`. The individual badge and heading elements are internal and are not a public override surface. The web keeps `.eg-tip-card`/`.tip` until an explicitly approved parity migration; nothing is migrated by this draft.
- **Reading order:** DOM order equals visual order — cover, badge, heading. The caption row never reorders against the cover, and the badge never moves below the heading.

## 3. Public API

| Prop / event | Type | Required | Default or rule | Description |
| --- | --- | --- | --- | --- |
| `title` | `string` | yes | — | Visible technical label in the caption row and the poster's accessible card name. Blank or whitespace-only warns in development and renders nothing. |
| `level` | `2 \| 3 \| 4 \| 5 \| 6` | no | `3` | Native heading rank only; the mono label typography never follows the rank. |
| `badge` | `string` | no | none (omitted) | Short category word rendered as a solid brand `Badge`. Whitespace-only renders no badge and leaves no empty pill. |
| `src` | `string` | yes | — | Cover image source, handed to `PhotoFrame`. |
| `alt` | `string` | yes | — | Cover alternative text carrying the real post text. Required and non-empty: the poster is the content, so it is never decorative. |
| `focalPoint` | `PhotoFrameFocalPoint` | no | `center` | Static cover crop alignment handed to `PhotoFrame`; crop only, never a mirror. |
| `className` | `string` | no | — | Outer layout only (grid/flex placement, width, margin), merged last through `cn()`. |
| part `className` | — | — | — | Not applicable: the card exposes no public part components in v0.1, so there is no per-part className surface. |

- **Prop conventions:** [canonical registry](../../../../skills/_shared/prop-naming.json) and [generated view](../../../prop-naming.md), looked up by meaning, name and alias before drafting. Applied approved entries: `title` → `heading-title`; `level` → `heading-level`; `focalPoint` → `image-focal-point`. `src` and `alt` are native image attributes with no own convention. `ratio` is deliberately not exposed (OQ-3), so the approved `aspect-ratio` entry is not applied here.
- **Retracted reuse:** an earlier draft of this spec applied the approved `thumbnail-badge` entry to `badge`. Re-checked against the registry, that entry is scoped to selectable visual options (“included in the option's accessible description”, sole usage `SelectTileOption`); a tip poster is not an option and its badge joins the card's content rather than an accessible description, so the reuse is retracted.
- **Proposed new convention (pending owner approval, not registered):** semantic ID `cover-badge`, name `badge`, meaning “short non-interactive category or flag annotation rendered as a `Badge` over or beside a media cover or poster, outside selectable-option semantics”; component-specific type `string`. The registry is not edited by this task: `skills/_shared/prop-naming.json` and `docs/prop-naming.md` are outside its edit surface, and a usage needs a `source` revision for a `types.ts` that does not exist yet. No exception is requested and no convention status changes.
- **Native props / refs:** the root forwards native `article` attributes (`data-*`, `aria-*` outside the protected set) and is merged last through `cn()` for outer layout only. `role`, `tabIndex`, `aria-label`/`aria-labelledby` (the heading names the card), `aria-pressed`/`aria-selected` and `style` are protected, following the `ProjectCard`/`ModuleCard` policy. No ref and no `asChild`: the poster is passive and its children are not cloned.
- **Controlled / uncontrolled:** Not applicable. The poster holds no state, no timers and no controls.
- **Compatibility:** new export surface (`TipCard` and `TipCardProps`, plus the re-exported `PhotoFrameFocalPoint` type where needed) added to `packages/ui/src/index.ts` under Molecules. Nothing existing changes; no token, dependency or legacy-class migration is proposed. React 18/19 consumption is a plan gate, not a claim of this draft. The catalog row's `composes` column (`AspectRatio, Text`) drifts from the actual reuse (`PhotoFrame`, `Badge`, `surfaceVariants`); that is an implementation-detail follow-up for the catalog generator in a separately approved future plan, not an approval blocker for this spec.

## 4. Behavior

| Initial state / action | Expected result | Emitted event |
| --- | --- | --- |
| Rendered with `title`, `src` and `alt` | Raised frame, reserved 2:3 cover, then one caption row holding the mono label; no empty badge slot and no placeholder boxes | none |
| `badge` supplied | A solid brand badge precedes the label in the caption row | none |
| `badge` absent or whitespace-only | No badge and no empty pill; the label keeps the row | none |
| `title` blank or whitespace-only | Development warning; the card renders nothing at all (a poster without a name is not a usable card) | none |
| Long `title` | The label wraps inside the caption row at word boundaries; it is never ellipsised, clamped or replaced by a tooltip (allowed difference from the web, which truncates with an ellipsis; see OQ-4) | none |
| Cover image fails to load | The reserved 2:3 box stays, so the caption row does not jump; the badge and label still render | none |
| Pointer over the poster | No movement, no zoom, no glow and no pointer cursor: the poster is passive; the web's active glow and hover zoom are omitted optional states (§6 intent) | none |
| `prefers-reduced-motion: reduce` | No change: the card defines no transition, transform or animation of its own | none |

- **States / representation:** no own `data-state`, no `data-active` and no mirrored state class. The root exposes `data-level` for debugging only; the visible axis is the badge's presence. Nothing in the card reacts to the host's current slide.
- **Limits / consumer responsibilities:** the consumer supplies every string and the image, decides the collection (a `Carousel` or the documented `TipsSlider` recipe), sets the poster width through the root `className`, and owns the counter, previous/next controls and progress. The card never fetches, links, sorts, animates or measures itself.

## 5. Accessibility

- **Accessible name / roles / relationships:** the root is a native `article` named by its generated heading through `aria-labelledby` with a `useId()` id; `level` keeps the surrounding outline valid. The cover `alt` carries the real post text, so the poster never depends on the category badge for meaning. The badge is plain text, never colour-only.
- **Keyboard / focus:** the poster adds no tab stop and no key handler and contains no interactive element. Moving between posters belongs to the host collection (`Carousel` implements the bounded arrow-key and control model), so there is never a nested focus target.
- **Announcements / other conditions:** no live region and no synthesized announcement; the host announces its own position changes. The full technical label stays readable because the DS wraps instead of truncating, which removes the web's “put the full name in `alt`/`title`” workaround. Touch targets: Not applicable — the poster exposes no control of its own.
- **Consumer obligations:** an image-only poster still needs its `alt` post text; a consumer that hides the label on narrow hosts must not remove the heading, because the heading is the card's name.

## 6. Appearance

| Variant axis | Allowed values | Default or rule | Combinations / restrictions |
| --- | --- | --- | --- |
| `level` | `2`–`6` | `3` | Rank never changes the label typography |
| `badge` | supplied / absent | absent | The badge is the only ink accent; no other axis changes it |
| `focalPoint` | the nine `PhotoFrameFocalPoint` values | `center` | Crop only; no mirroring, no per-instance filter |
| presentation | one presentation | — | No `variant`, `size` or `active` axis in v0.1 (the web's active/coverflow states are excluded as omitted optional states, §6 intent); poster width is consumer layout |

- **Tokens / Material:** the root composes the public `surfaceVariants({ tone: 'surface-1', elevation: 1, padding: 'sm', radius: 'xl' })` recipe — the same raised Grafito frame as `ProjectCard` — plus own layout classes (`flex min-w-0 flex-col gap-3`). This satisfies the no-flat-replacement rule with an already-approved recipe instead of the web's handwritten shadow, and `docs/MATERIAL.md` prescribes no header band for TipCard, so the poster stays a single surface (OQ-1 records the bare-poster alternative). The cover is the public `PhotoFrame` with a fixed numeric `ratio` of `2 / 3` and the supplied `focalPoint`. The caption row uses existing recipes only: `Badge` (`tone="brand"`, `variant="solid"`) for the category and `font-mono text-label-default text-fg-default` with `wrap-anywhere` for the technical label. The web's deep black drop shadow, brand-alpha poster border and black gradient scrim are **not** reproduced: the shadow and border have no approved recipe and the scrim would need one (prerequisite gaps, OQ-2/OQ-1 of the source treatment).
- **Dynamic geometry:** Not applicable. The 2:3 proportion is a fixed numeric `PhotoFrame` ratio resolved by the public `AspectRatio` primitive; the card introduces no custom property, no interpolated class string and no inline geometry.
- **Motion:** none. The web's 1.04 image zoom on the active poster and its brightness/rotation coverflow are not ported (omitted optional states, deferred to a separately approved `TipsSlider` amendment); anything added later must be suppressed under `prefers-reduced-motion` and must not animate layout.
- **Class composition / consumer layout:** the root merges `className` last through `cn()` for outer placement, width and margin; `twMerge` resolves recognised utility conflicts only, so there is no universal last-class-wins promise, no appearance-override permission and no per-instance recipe. `surfaceVariants` remains the frame appearance API and `PhotoFrame` the cover appearance API.
- **Files / pending proposals:** the six mandatory files are planned at `packages/ui/src/molecules/tip-card/` — `types.ts` (CVA recipes, `TipCardProps`, English JSDoc with `@control` on every own declaration), `useTipCard.ts` (title/badge normalization, protected props, derived heading id, per-part `cn()`), `TipCard.tsx` (JSX only), `TipCard.test.tsx`, `TipCard.stories.tsx` (`Molecules/TipCard`, English) and `index.ts`. **No stylesheet** and no extra internal module. No token or dependency change is proposed. Pending token proposals reported, not added: a mono label recipe (v0.1 composes `--font-mono` with `--text-label-default`), a caption scrim/overlay recipe (OQ-2) and a deep-shadow media-poster recipe (OQ-1, only if the bare web look is required).

## Blocking decisions for the owner

| ID | Question | Recommendation |
| --- | --- | --- |
| OQ-1 | Which poster frame: the proposed raised `surface-1` recipe (`surfaceVariants({ tone: 'surface-1', elevation: 1, padding: 'sm', radius: 'xl' })`, approved and compliant today), the web's brand-alpha hairline plus deep black drop shadow, or a bare poster with no Material paint at all? | Use the raised `surface-1` recipe. The web's shadow is a handwritten value Material forbids and no approved media-poster recipe exists, while a bare poster would be exactly the flat replacement the rules reject; the frame is available now and the web look can return later only through an approved recipe. |
| OQ-2 | Does the caption sit below the poster (a plain row) as proposed, or must it overlay the bottom of the image as the web does? An overlay needs a scrim: the web uses a black gradient that Material forbids hand-writing, and no scrim/overlay recipe or token exists for media captions. | Keep the caption below the cover in v0.1. An overlay is worth doing only with an approved Material overlay/scrim recipe or a new token, which is a separate proposal; the poster's identity survives without it. |
| OQ-3 | Is the 2:3 proportion fixed by the component, or should `TipCard` expose a `ratio` prop like `PhotoFrame` does? | Fix 2:3. A tip poster is a defined format, and re-exposing `PhotoFrame`'s ratio axis inside a specialised poster would duplicate a public axis and weaken the component's promise. A different format is a different component. |
| OQ-4 | Should the technical label wrap as proposed, or truncate with an ellipsis as the web does? | Wrap. Truncation hides supplied content, forces the web's workaround of repeating the label inside `alt`/`title`, and puts the full name out of reach; wrapping keeps the accessible name complete. The capture records the web's truncation so the difference stays visible. |
| OQ-5 | Is the root `article` + generated heading (as proposed), or native `figure`/`figcaption` semantics with the label as the caption? | Keep `article` + heading. The label is the card's accessible name in a slider context and the `level` rank keeps the surrounding outline valid; `figure`/`figcaption` names the figure in some assistive technology but loses the heading rank and the naming guarantee. Either way the caption row's visual caption role is a styling matter, and this stays a proposal the owner can reverse before approval. |
