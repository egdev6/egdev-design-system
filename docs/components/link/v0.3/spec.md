## 1. Purpose and scope

**Delta against the implemented v0.2 appearance.** The shipped Link is one standalone text navigation atom: native anchor or Radix Slot child, decorative trailing arrow that **always points right**, hidden new-tab notice, brand text with **no underline** (`pb-0 border-0` reset the legacy rule), and a horizontal arrow nudge on hover. #175 decided exactly that in its own words: "Keep the up-right arrow for external links only — rejected by the owner: the arrow always points right" and "Colored text only: remove the bottom border treatment".

The web reads differently. Every link the web and the Foundation component draw carries a 1px brand underline and a direction-specific arrow, so a new web view rebuilt from the design-system atom would silently lose both cues: it could not reproduce the recorded `arrow-up-right` affordance, and it could not draw the underlined treatment. v0.3 closes **only** that expressiveness gap, as opt-in inputs, without changing any default:

- **Need / non-goals:** (a) let a consumer show the external/off-site cue (`arrow-up-right`) the web uses, without reversing #175's default direction; (b) let a consumer draw the brand underline the web and the legacy `.eg-link` rule use, without reversing #175's borderless default. Non-goals: changing the default arrow direction or making underline the default; a `tone`, `size`, `mode`, `icon` or `variant`-beyond-the-two-listed appearance; a non-interactive "link look" (Q3); prose/inline paragraph links; navigation menus (Menu/NavList own them); icon-only links (IconButton `asChild`); primary actions (Button); hover motion changes (Q5); `external`/`newTabText`/`asChild`/ref semantics; serializer or router integration; new tokens, dependencies, primitives or stylesheets; any change to legacy `.eg-link` CSS or a `.link`→`eg-link` web migration.
- **Cataloging decision / alternatives:** **variant** of the existing atom (step 2 of `docs/CATALOGACION.md`), not a new component. *Reuse* rejected: no other atom draws an underlined text link or a direction-selected trailing arrow; `Badge`, `Chip` and `Button` are different responsibilities and different Material recipes. *Compose* rejected: a consumer wrapping `Link` in private CSS would duplicate the recipe in the app and put appearance outside the component contract (and `className` is documented as outer-layout-only, not an appearance surface). *Extract* rejected: nothing is hidden inside another component. *New* rejected: no new responsibility, level, package or Radix base. Evidence for the gap, from the read-only sources: `reference-web/pulso-source.html` rule block `.link{…border-bottom:1px solid var(--r45);padding-bottom:2px…}` (line 74) and `.link:hover{border-color:var(--neon);color:var(--red-200)}` (line 75) with `.link .i{width:18px;height:18px}` and `.link:hover .i{transform:translate(2px,-2px)}` (lines 76–77); the page renders 9 `a.link` anchors and 1 `span.link`, of which 7 anchors use the `#i-arrow-ur` (up-right) glyph and 2 anchors plus the span use `#i-arrow-r`; `design-system/components/Link/README.md` documents `icon: "arrow-right" | "arrow-up-right" | "none"` ("Flecha interna o externa") and the "subrayado rojo que se enciende a neón en hover"; `design-system/components/Link/preview.html` renders the same three rows (external, internal, no icon), all underlined; `design-system/components/bundle.css:71-82` ships the identical `.eg-link` rule set. ## 2. Anatomy and composition

One root anchor; the label, arrow and notice are unchanged parts. The underline is root paint, not a new part.

| Part | Responsibility | Native element / Radix primitive | Allowed content |
| --- | --- | --- | --- |
| Root | Navigation target, public marker, text and underline paint | native `<a>`; `SlotPrimitive.Root` when `asChild` | Label plus the parts below |
| Label | Accessible name and visible text | `children` inside `SlotPrimitive.Slottable` | Descriptive text; exactly one anchor element with `asChild` |
| Arrow | Decorative direction cue | Icon atom, `size='sm'`, `aria-hidden` | `arrow-right` (default) or `arrow-up-right` (`arrowGlyph='up-right'`); omitted when `arrow` is false |
| New-tab notice | Screen-reader hint | `VisuallyHiddenPrimitive.Root` | `newTabText`, rendered only when `external` |
| Underline | Brand cue under the label (`variant="underlined"` only) | root `border-bottom` | none; paint only, never a child element |

- **Radix / composition:** unchanged: `@radix-ui/react-slot` (`Slot`, `Slottable`) and `@radix-ui/react-visually-hidden`, both already direct dependencies. No new primitive, no `asChild` change, no plural anchors.
- **Public markers:** `eg-link` stays on the root in both variants, so legacy selectors and consumers keep working; the legacy `.eg-link` rule in `packages/ui/src/styles/legacy/bundle.css` remains untouched and continues to coexist (component utilities win for the properties they set). No public part markers, no `data-testid`, no new root class per variant (the variant is a class set, not a marker; theming uses the root marker plus the existing utilities).

## 3. Public API

- **Prop conventions:** registry source `skills/_shared/prop-naming.json`, generated view `docs/prop-naming.md`, consulted by meaning, name and aliases before drafting. Two inputs are added; **no existing prop changes type, requiredness or default**.

| Prop / event | Type | Required | Default or rule | Description |
| --- | --- | --- | --- | --- |
| `children` | `ReactNode` | Yes | None | Descriptive visible label; with `asChild`, exactly one anchor-compatible element that spreads props and forwards its ref. Unchanged. |
| `asChild` | `boolean` (discriminated union) | No | `false` | Renders the single child through Radix Slot; the child owns `href`. Unchanged; reuses `slot-composition`. |
| `href` | `string` | Yes unless `asChild`; `never` with it | None | Native destination. Unchanged. |
| `external` | `boolean` | No | `false` | Forces `target="_blank"`, merged `rel` with `noopener noreferrer`, and the hidden notice. Unchanged and still **does not** choose the glyph; reuses `new-tab-navigation`. |
| `newTabText` | `string` | No | `(opens in a new tab)` | Localized hidden notice, rendered only when `external`. Unchanged; reuses `new-tab-notice`. |
| `arrow` | `boolean` | No | `true` | Show or hide the trailing decorative arrow, independent of `variant` and of `external`. Unchanged; reuses `trailing-arrow`. |
| `arrowGlyph` | `LinkArrowGlyph` (`'right' \| 'up-right'`) | No | `right` | **New** closed-set glyph choice for the trailing arrow, mapped to Icon `arrow-right` / `arrow-up-right`. Ignored when `arrow` is false. Proposed convention `trailing-arrow-glyph` (see below). |
| `variant` | `LinkVariant` (`'plain' \| 'underlined'`) | No | `plain` | **New** appearance axis: `plain` is the approved v0.2 look; `underlined` adds the brand underline. Reuses `visual-treatment`. |
| `className` | `string` | No | Absent | Inherited root attribute; outer margin/alignment only, merged last by `cn()`. Appearance overrides remain unsupported. Unchanged. |
| Native attributes / ref | `a` props; `forwardRef<HTMLAnchorElement>` | No | Forwarded to the root | `id`, `title`, `data-*`, compatible `aria-*`, `onClick`, `target`, `rel`; the actual target is the anchor in both native and Slot modes. Unchanged. |

```ts
export type LinkVariant = 'plain' | 'underlined';
export type LinkArrowGlyph = 'right' | 'up-right';

type LinkTargetProps =
  | { asChild?: false; href: string }
  | { asChild: true; href?: never };

export type LinkProps = Omit<ComponentPropsWithoutRef<'a'>, 'href' | 'children'> &
  LinkTargetProps & {
    children: ReactNode;
    external?: boolean;   // default false
    newTabText?: string;  // default (opens in a new tab)
    arrow?: boolean;      // default true
    arrowGlyph?: LinkArrowGlyph; // default 'right'
    variant?: LinkVariant;       // default 'plain'
  };
```

- **Prop conventions applied (exact IDs):** `slot-composition` (`asChild`), `new-tab-navigation` (`external`), `new-tab-notice` (`newTabText`), `trailing-arrow` (`arrow`), `visual-treatment` (`variant`, new Link usage). All five are `approved`; the four Link usages already carry a source revision, and `variant` adds a new Link usage with `source: {path: packages/ui/src/atoms/link/types.ts, symbol: LinkProps, revision: sha256:<reviewed file hash>}` in the implementation commit. Convention approval stays separate from this spec and from the issue.
- **New convention candidate (proposed, not approved):**

```json
{
  "id": "trailing-arrow-glyph",
  "name": "arrowGlyph",
  "meaning": "The explicit glyph of a component's trailing direction arrow, chosen from a closed set the component owns, when a consumer must reproduce a source design's cue.",
  "whenToUse": "A text link must show the off-site/external cue (up-right) that its source design uses, while the component default keeps pointing right.",
  "avoid": "Arbitrary icons or icon nodes (use leading-icon and slots for consumer content), a trailing-icon permission, or a boolean that duplicates the component's own default derivation.",
  "status": "proposed",
  "approval": null,
  "aliases": [],
  "exceptions": []
}
```

  If Q1 adopts this, the approved `trailing-arrow` entry's phrase "the glyph is derived by the component" needs a scoped clarification naming `arrowGlyph` as the consumer override; that is a separate convention-level change with its own approval and is neither performed nor presumed here.
  Rejected reuse: `icon-glyph-name` (`name`) is the Icon atom's own required glyph prop, not a trailing slot of another component; `leading-icon` (`icon`) is explicitly leading and its registry meaning forbids trailing icons outside its scoped exceptions, so it cannot describe a trailing arrow; `icon-placement` (`iconPosition`) selects a position, not a shape; `trailing-arrow` (`arrow`) is a visibility boolean whose meaning ("the glyph is derived by the component") would be contradicted by widening it to a union. Rejected alternative shapes: `arrow: boolean \| 'right' \| 'up-right'` (merges visibility with direction and breaks an approved usage type); deriving the glyph from `external` again (it is v0.1 D3, and #175 explicitly rejected it — see Q1); an `IconName`-typed override (arbitrary glyphs, and it collides with the leading-icon registry rule).
- **Native props / refs:** unchanged inherited anchor props and `forwardRef<HTMLAnchorElement>`; the arrow and notice never receive consumer props.
- **Controlled / uncontrolled:** Not applicable: Link has no own state.
- **Compatibility (additive):** `plain` and `arrowGlyph='right'` are the current behavior, so every existing consumer, story, test and snapshot keeps its emitted classes, glyph and accessible name. New public types `LinkVariant` and `LinkArrowGlyph` are added to `index.ts` and are reachable through `packages/ui/src/index.ts`. `LinkProps` keeps its href union, so no consumer needs narrowing. Unknown runtime values for `variant`/`arrowGlyph` normalize to the defaults (no throw), matching the atom's existing runtime-boundary behavior. No token, dependency, primitive, legacy-CSS or consumer change.

## 4. Behavior

| Initial state / action | Expected result | Emitted event |
| --- | --- | --- |
| Default render | One `a.eg-link` with `href`, right arrow at Icon `sm`, no underline utilities, accessible name = label | None |
| `variant="underlined"` | Same root and behavior; the root additionally resolves the brand underline and the hover underline ink | None |
| `arrowGlyph="up-right"` | The arrow renders the up-right glyph; DOM order, size, `aria-hidden` and motion are unchanged | None |
| `arrow={false}` with any `arrowGlyph` | No arrow is rendered; `arrowGlyph` has no observable effect | None |
| `external={true}` with the default glyph | New tab + safe `rel` + hidden notice, arrow still points right (v0.2 default preserved) | `onClick` if supplied |
| `external={true}` with `arrowGlyph="up-right"` | Same new-tab semantics; the arrow now shows the external cue | `onClick` if supplied |
| Hover / focus-visible | Unchanged: brand-to-red-200 text change, `--shadow-focus` ring, horizontal arrow nudge; `underlined` additionally switches the underline ink to brand-default | None |
| Reduced motion | Unchanged: no translate, no transition | None |
| `asChild` with a router anchor | Unchanged composition: marker, variant classes, arrow and notice land on the child; the child owns `href` | Child and parent handlers |
| Runtime value outside the unions (cast) | Ignored: falls back to `plain` / `right`; no error, no partial class set | None |

- **States / representation:** no own `data-state`; `:hover`, `:focus-visible`, `aria-*` and `data-*` stay native. The variant is a static class set; it is never mirrored into a state attribute, and the underline is never expressed as `text-decoration`.
- **Limits / consumer responsibilities:** `arrowGlyph` does not replace `external` (the new-tab contract still requires `external`); `variant` is a paint axis only and must not be used to imply interactivity or to hide the difference between a link and plain text; consumers keep `className` for outer layout only; the destination, `aria-current`, router interception and localization of `newTabText` stay consumer-owned.

## 5. Accessibility

- **Accessible name / roles / relationships:** unchanged role `link`; name = label text (+ hidden `newTabText` when `external`); the arrow stays `aria-hidden` and unfocusable in both variants and both glyphs. `underlined` adds no text, no landmark and no relationship.
- **Keyboard / focus:** unchanged native Tab/Enter navigation and `focus-visible:[box-shadow:var(--shadow-focus)]` with `rounded-sm`; the underline does not alter the focus ring, tab order or hit area, and no key handling is added.
- **Announcements / other conditions:** the new-tab notice remains the only announcement, and `external` still needs it because #175 removed the visual external cue from the default; `arrowGlyph="up-right"` is a decorative visual cue only. Non-color cues: the underline is a shape change, not colour alone; neither variant may rely on colour for the hover state. Contrast: `plain` keeps the owner-accepted "Todo neón" ink (`--color-fg-brand-raised` = neon, AA only on the canvas; documented in `theme.css`), and the `underlined` variant does not change that ink — the web instead uses white text with the brand underline (Q4). Real contrast measurements remain part of the implementation plan and must not be inferred from the captures. Touch target size is unchanged and consumer-owned.

## 6. Appearance

| Variant axis | Allowed values | Default or rule | Combinations / restrictions |
| --- | --- | --- | --- |
| `variant` | `plain`, `underlined` | `plain` | Both accept every other prop; `underlined` only adds underline paint, never removes the arrow or the text paint. |
| `arrowGlyph` | `right`, `up-right` | `right` | Only meaningful when `arrow` is true; independent of `external` and `variant`. |
| `arrow` | `true`, `false` | `true` | Visibility only. |
| Size / tone / mode | none | — | No new axis; one size, one ink family, no static/link-look mode (Q3). |

- **Tokens / Material:** both variants stay in the approved borderless-or-line text recipe with existing tokens and no new Material treatment, no handwritten shadow, gradient, colour or spacing value. One shared base carries the unchanged text recipe — `eg-link group/link inline-flex items-center gap-2 font-sans text-label-default text-fg-brand-raised no-underline cursor-pointer transition-colors duration-(--duration-fast) ease-(--ease-out) hover:text-primitive-red-200 focus-visible:outline-none focus-visible:[box-shadow:var(--shadow-focus)] focus-visible:rounded-sm motion-reduce:transition-none` — and the legacy border/padding reset moves **into the `plain` branch**, which adds `pb-0 border-0`. That keeps `plain` resolving the same utility set and values as today (verified against the project's extended `cn()`: identical set, ordering only differs). `underlined` adds the legacy/web underline instead: `border-b border-border-brand pb-0.5 hover:border-fg-brand-default`. The reset must not live in the shared base: `border-0` and `border-b` are different `tailwind-merge` groups, so the extended `cn()` keeps both and the rendered 1px underline would then depend on emitted CSS order. The implementation plan must prove both emitted class sets with a CVA/`cn()` assertion and an emitted-CSS check. Token backing: `--color-border-brand` is `var(--color-alpha-red-45)` = `rgba(255,0,54,.45)`, which is exactly the computed web underline colour; `--color-fg-brand-default` is neon, exactly the computed hover underline colour; the legacy 2px bottom inset is one half of the 3.2px spacing unit (`--spacing: var(--space-1)`), so `pb-0.5` = 1.6px, the #218-scaled equivalent of the legacy 2px. The arrow recipes (`linkArrowVariants`) are unchanged: the up-right glyph inherits the same `self-center shrink-0 transform-none … motion-safe:group-hover/link:translate-x-1` set, so the nudge stays horizontal (Q5). No token value changes, no dependency, no legacy CSS edit.
- **Dynamic geometry:** Not applicable. No inline style, no custom property, no interpolated class string.
- **Class composition / consumer layout:** `className` still merges last on the root through `cn()` for outer margin/alignment; `eg-link` survives in both variants; per-part override surfaces do not exist (the arrow and notice stay internal). A consumer utility that collides with the underline is a documented limitation, not a supported appearance override: for example, a consumer `border-b` does not remove the recipe's `border-0` through the extended `cn()`, so the resulting paint depends on emitted CSS order — use `variant="underlined"` instead of consumer utilities.
- **Files / pending proposals:** the six mandatory files keep their roles — `types.ts` (adds `LinkVariant`, `LinkArrowGlyph`, the new JSDoc with `@control` tags, a `variant` key in `linkVariants` whose `plain` branch now owns the `pb-0 border-0` reset, and no change to the arrow CVA), `useLink.ts` (normalizes the glyph to the Icon name and validates/normalizes the variant), `Link.tsx` (passes the derived glyph), `Link.test.tsx`, `Link.stories.tsx` (adds `Underlined`, `ExternalUpRight` and one composition story showing a card footer with the web treatment), `index.ts` (adds the two type exports). **No stylesheet**, no additional internal module, no dependency change, no token change. Documentation outside this folder that would become stale is proposed separately in the implementation plan: `docs/components/link/v0.2/amendment.md` (still says "No public prop is added") and the web's own `.link` rule, which is not touched here.

### Open questions for owner approval (blocking)

- **Q1 — External up-right glyph (blocking).** The web and the Foundation component use `arrow-up-right` for off-site destinations and `arrow-right` for internal ones (VIS-01/VIS-03/VIS-05/VIS-07; 7 up-right anchors vs 2 right anchors in the reference page), and the approved catalog draft lists "External `arrow-up-right` affordance" as a Link variant gap. But #175 explicitly rejected that derivation: "Keep the up-right arrow for external links only — rejected by the owner: the arrow always points right". Options: (a) the proposed opt-in `arrowGlyph?: 'right' | 'up-right'`, default `right`, so the approved default is untouched and a web view can request the cue; (b) restore v0.1 D3 and derive the glyph from `external`, which reverses #175; (c) decline entirely and close this part of the catalog gap as a deliberate divergence, accepting that sighted users no longer get a visual external cue after #175. *Recommendation:* **(a)** — it satisfies the owner-approved catalog gap without overriding the owner's later rejection, and it keeps the visual cue available where the web genuinely needs it. If the owner actually wants the cue everywhere, (b) is the smaller API and the cleaner promise, but it must be stated as superseding #175.
- **Q2 — Underline treatment (blocking).** The reference page and the Foundation preview draw a 1px `--color-border-brand` underline under every link that turns neon on hover (VIS-01 to VIS-08), and the legacy `.eg-link` rule in this repository still ships the same thing; #175 removed it for the atom ("Colored text only: remove the bottom border treatment"), and the approved catalog draft did not record it as a gap. Options: (a) the proposed opt-in `variant?: 'plain' | 'underlined'`, default `plain` (recommended shape if the web parity is wanted); (b) make `underlined` the default, which reverses #175 and changes every existing consumer's appearance; (c) decline and record the underline as a superseded web/legacy treatment, accepting that migrated web views will look different from today's page. *Recommendation:* **(a)** if the owner still wants the web's link look available to web views; **(c)** if the borderless neon link is now the intended look everywhere, in which case this version reduces to Q1 and the underline captures stay as history.
- **Q3 — Non-interactive link look inside a whole-card anchor (non-blocking here).** `pulso-source.html` renders `<span class="link">Leer artículo …</span>` inside the article-feature anchor (VIS-08): the link *look* without link semantics. `Link` is an anchor atom and a static mode would mirror the still-unapproved `render-mode` proposal from Chip v0.2. *Recommendation:* do not add a Link mode; record it as an input for the card/list layer (ArticleFeature/BlogGrid, layer (c)), where the whole-card anchor owns navigation.
- **Q4 — Ink of the `underlined` variant on raised surfaces (advisory).** The web uses white labels over the brand underline; the design-system atom uses `--color-fg-brand-raised` (neon), which the owner accepted in "Todo neón" even though neon small text only meets AA on the canvas, not on surfaces 1–3 (`theme.css` comment). *Recommendation:* keep one ink for both variants (no second ink promise) and record the documented neon limitation as a known, owner-accepted constraint; if `underlined` is meant mainly for cards on surface-1, switching that variant to `text-fg-default` with the brand underline would restore AA and match the web exactly — but that is a separate appearance promise and needs its own decision.
- **Q5 — Hover motion (advisory).** The web and the legacy rule move the arrow diagonally (`translate(2px,-2px)`, VIS-02/VIS-06); v0.2 decided "the arrow moves slightly to the right" and v0.3 keeps that. *Recommendation:* keep the horizontal token-backed nudge for both variants and record the diagonal move as a superseded legacy detail; no motion change in v0.3.

**Next step:** the owner answers Q1 and Q2 (and decides on Q3–Q5), adopts or revises the proposed captures, and approves this exact version; only then may an implementation plan be proposed, with its own approval, and no token, dependency or catalog change is authorized by this spec.
