## 1. Purpose and scope

**Proposal.** Extend the pointer target of the existing `@egdev/ui` IconButton without enlarging its visible control or changing its in-flow layout box. Recommend doing so automatically for every enabled size, including `lg`, and for every pointer, with no new prop. This repairs the existing touch-layout promise rather than making a caller discover a new opt-in. The larger target is a square, including around the round `outline` treatment; its corners are invisible. The consumer still has to provide an unobstructed, non-overlapping region. Final API, input policy and geometry remain owner decisions below.

**Cataloging.** Reuse and amend the exported IconButton atom: it already owns one named action and the relevant size, treatment and Slot behavior. Reuse unchanged cannot meet the recorded target promise; another visual size or variant would change the visible geometry or conflate geometry with appearance. An app wrapper would duplicate the fix and could change layout, focus and Slot semantics. Extraction or a new component adds no distinct responsibility. ListItem continues to own row layout and composition, not the IconButton target.

**Evidence — inspected, not a runtime measurement.**

- `packages/ui/src/index.ts:13` and `packages/ui/src/atoms/icon-button/index.ts:1` export the existing atom and its public types. `packages/ui/src/atoms/icon-button/types.ts:5,28-33,64` defines `sm | md | lg`, `size-8/10/12`, and the existing promise: "touch layouts provide a hit area of at least 44px." Under the default token scale these visible border boxes are 25.6, 32 and 38.4 CSS px, respectively (`packages/tokens/src/theme.css:454-458,589-593`); even `lg` is below 44px. The existing CVA contains no hit-area expansion (`types.ts:50-65`). These are source-derived values, not observed browser results.
- `types.ts:51` also applies a motion-safe `scale-94` on active press. A 44.8px descendant hit rectangle scaled with the root would become 42.112px; merely sizing a pseudo-element to `size-14` cannot establish the minimum during press. Reduced-motion behavior and the existing press appearance must be preserved.
- `IconButton.tsx:8-14` uses one native or slotted root and Radix AccessibleIcon; `useIconButton.ts:34-40,54-69` supplies disabled guards and event forwarding. `IconButton.test.tsx:52,100-163,205-214` has existing native, Slot, disabled and focus/press coverage, not browser geometry proof.
- The #540 triage comment records the owner's invisible-area decision and asks how it is enabled, how neighboring targets avoid overlap, and how focus and Material are handled. [Recado #41](https://github.com/egdev6/recado/issues/41) identifies this request and [#538](https://github.com/egdev6/egdev-design-system/issues/538) as issue-backed mitigations. Per `odd/tasks/consumer-request-specs.md:9-10,22-23`, both originate in the same compact note card: a two-line ListItem with a trailing icon action. Keep the Recado TODO/allowlist mitigation until the relevant design-system change ships and the consumer independently verifies removal.

## 2. Anatomy and composition

| Part | Proposal | Semantics / compatibility |
| --- | --- | --- |
| Root | Existing visible native `button`, or the supported empty anchor/router host through Radix Slot | `eg-icon-btn`, native/slotted ref, props and event ownership remain on the same root. No wrapper or extra focus stop. |
| Invisible extension | Prefer one empty, absolutely positioned root pseudo-element, centered and square, with transparent paint | Pointer hit region belongs to the root; no accessible node, role, name or public part marker. It must not clip or obscure the focus ring. |
| Icon and hidden name | Existing Radix AccessibleIcon composition | Decorative glyph remains hidden; `label` remains the sole required name input. |

This is a feasibility proposal, not proof that a pseudo-element works with every host. `asChild` still requires one compatible host that spreads props and forwards its ref (`types.ts:35-46`); native anchors and router anchors must be checked. A child that already owns the selected pseudo-element, clips overflow, or changes positioning/stacking can conflict: do not silently drop the target or overwrite its presentation. Resolve such conflicts in the separate plan or document and approve a precise compatibility restriction before implementation. No new Radix primitive is needed.

## 3. Public API

| Existing API | Proposal / compatibility |
| --- | --- |
| `size?: 'sm' \| 'md' \| 'lg'`, default `md` | Remains the **visible** control/glyph preset. All three get the proposed extension; do not add or rename a size. |
| `variant?: 'ghost' \| 'outline' \| 'primary' \| 'secondary'`, default `ghost` | All treatments get identical target semantics. `outline` remains round; the others retain their existing radius. There is no `round` prop and none is proposed. |
| `label: string`, `icon: ReactElement`, `asChild?: boolean`, `children?: ReactElement` | Types, requiredness, default `asChild=false`, hidden naming, decorative icon and Slot restrictions remain unchanged. |
| Native `disabled`, events and attributes, `className`, ref | Existing native/slotted disabled semantics and event forwarding remain; `className` remains root outer layout only, merged with `cn()`, not an appearance or target override. The ref remains on the actual host; no new ref type or export. |

**Recommended enablement: automatic, no prop.** A change from today's effective target can alter `event.target`, pointer-enter/hover boundaries and which nearby control or row receives a click even though the component itself causes no in-flow layout shift. Consumers may need to change spacing, which *can* shift their layouts. A transparent rectangle is not automatically non-intercepting or safe merely because it is invisible. Audit dense consumers and provide the spacing rules below before adopting this behavior.

**Alternative — opt-in:** `extendHitArea?: boolean`, proposed default `false`, applies the extension only when true. This avoids changing existing hit testing until the caller opts in, but omitted/false controls, including `lg`, retain the broken touch promise; it does **not** satisfy the requested universal fix without an explicit owner decision to narrow that promise and update its documentation. Defaulting true with a false opt-out instead preserves the automatic default but permits intentionally undersized targets and introduces an API/contract exception. Neither alternative is approved.

**Prop naming lookup.** Consulted the [registry source](../../../../skills/_shared/prop-naming.json) and [generated view](../../../prop-naming.md) by meaning, name and aliases for hit area, touch target, hitbox, target size, size and density. Existing approved `preset-dimensions` / `size` (`skills/_shared/prop-naming.json:737`, `docs/prop-naming.md:180`) selects visible dimensional presets; it does not name a separate invisible target. `visual-treatment` / `variant` (`prop-naming.json:1014`) is appearance, not hit geometry. Density references describe component size or unrelated effect profiles, not target expansion. Existing `accessible-name`, `leading-icon` and `slot-composition` stay unchanged (`prop-naming.json:1606,2591,2852`).

If the owner selects opt-in, propose **new**, not registered or approved: semantic ID `hit-area-extension`, canonical name `extendHitArea`, component-specific `IconButton` type `boolean`, optional, proposed default `false`; meaning: enable a larger invisible pointer target without changing visible dimensions or layout. No exception is proposed. Reviewed baseline source: `{ path: 'packages/ui/src/atoms/icon-button/types.ts', symbol: 'IconButtonProps', revision: 'sha256:9018d3d7c164e7858bd40a937af4cf968fa0ccb4ee32c3820abf6ca048109f75' }`; this identifies the existing type and does **not** claim the prop exists. Convention approval, a future reviewed usage/source revision and registry integration require separate authorization. The recommended automatic option needs no new entry or exception.

Controlled/uncontrolled state is not applicable. No new prop, default, export or registry change is approved by this draft.

## 4. Behavior

**Proposed target and input policy.** For every enabled IconButton, on every pointer type, make the centered usable target at least 44 × 44 CSS px. With default tokens, propose a 44.8 × 44.8px square using `--space-14` / `--spacing-14`. Its rest-state outsets from each visible edge are 9.6px (`sm`), 6.4px (`md`) and 3.2px (`lg`). The minimum applies to the actual clickable region, not just a declared width or a circle's bounding box. The target must remain usable across pointer-down, active feedback and release, without moving the pointer, including points inside the outer corners of a centered 44 × 44px square. A touch must not turn into a neighboring action or a duplicate activation.

| Action / condition | Proposed result |
| --- | --- |
| Pointer enters and activates an enabled extension | The same root action or slotted link receives one native activation; existing callbacks, navigation and event propagation remain. The extension may cause hover/tooltip triggering earlier than the visible boundary. |
| Keyboard Tab, Enter or Space | Existing native button behavior remains; a link retains native link keys. The extension is not independently focusable and adds no keyboard handler. |
| Disabled native button or slotted host | Existing `disabled` or `aria-disabled`, `data-disabled`, tab-order and activation guards remain. The extension must not independently receive pointer events; preserve the existing disabled `pointer-events: none` policy. Events may fall through to underlying content, so a host must not depend on a disabled target blocking its row. |
| Tooltip wraps the button | Existing Radix Tooltip trigger/ref and supplementary description remain; pointer entry may occur over the extension. Do not promise a tooltip opens on touch or becomes the accessible name. |

**Implementation direction, subject to plan review.** Prefer a static token-backed, empty `::after` on a positioned root, inheriting disabled pointer behavior and routing native pointer input to that root. It must have no background, border, shadow or focus appearance. Validate the actual hit-tested square and the interaction with root transitions, active `scale-94`, reduced motion, stacking, clipping, Slot and a child's own pseudo-elements. A pseudo-element is transformed with its ancestor; the plan must demonstrate a compliant way to keep the required region effective throughout press and release, not assume a declared 44.8px remains 44.8px. If that cannot be shown without changing visible press feedback, stop for a revised proposal; `--space-16` (51.2px at rest, 48.128px at steady 0.94 scale) is a possible larger-token fallback, with increased overlap and press-edge risks, not an approved automatic substitution. In either case test the complete down/up sequence, including the boundary of the promised square. No custom event forwarding, synthetic click, new inline geometry or dynamic utility-string interpolation is authorized here.

Padding plus negative margins is an alternative, but rejected as the recommendation: even if it preserves a flex/grid footprint, it changes the button border box, native ref geometry, focus/shadow boundary and potentially clipping/Slot layout. It does not meet this proposal's unchanged visible-root box without a separately reviewed structural solution.

**Pointer policy alternatives.** `@media (pointer: coarse)` limits interception on a fine primary pointer and matches the existing Slider precedent (`packages/ui/src/atoms/slider/types.ts:74-76`), but can miss touch on hybrids whose primary pointer is fine. `@media (any-pointer: coarse)` also covers a secondary touch capability, but expands mouse hit testing on such devices and does not identify each event's input type. Always-on covers hybrids and avoids media-query detection gaps, but changes fine-pointer hit testing everywhere. Recommend always-on; the owner must select the policy, not infer it from this draft.

**Overlap and host responsibilities.** Expanded targets must not overlap any other interactive hit region, including neighboring rows, links, drag handles or controls. For horizontally aligned controls with overlapping vertical ranges, the visible edge-to-edge gap must be at least the sum of their outsets: two `sm` buttons need 19.2px, two `md` need 12.8px, and two `lg` need 6.4px under the proposed default tokens. Mixed sizes use the sum of their respective outsets. These are illustrative minima for the proposed 44.8px rectangle, not automatic layout or collision detection. Actual target regions, stacking, writing direction and vertical gaps must also be checked; an unrelated overlay or clipped ancestor can invalidate the guarantee. In particular, ListItem's existing action `gap-1` is 3.2px (`packages/ui/src/molecules/list-item/types.ts:219` and `packages/tokens/src/theme.css:440`), insufficient for two adjacent `lg` targets under this proposal.

For the shared Recado two-line card, keep the trailing IconButton an independent action; reserve its full target in the row, separate from the text/link or row action. Never nest it in a whole-row anchor; ListItem's contract explicitly keeps actions out of that anchor (`packages/ui/src/molecules/list-item/types.ts:84-85`). With the proposed 44.8px target, a centered action needs at least 44.8px of unobstructed vertical space and row-to-row center separation, or equivalent non-interactive gap; a shorter row may retain its height only if the full target can extend into reserved, unclipped space without touching the next row's target. The atom itself does not increase row height. If the owner chooses a larger target, reserve that actual extent instead. This amendment neither changes ListItem nor decides #538's text contract.

## 5. Accessibility

- Preserve the same accessible name, role, hidden icon, descriptions, disabled semantics and keyboard/focus order; an invisible target adds no name, role, live region or focus stop. A tooltip remains a supplementary description (`packages/ui/src/atoms/tooltip/types.ts:5-17`).
- Focus-visible remains on the **visible button boundary**, not the larger invisible square: the existing `--shadow-focus` has priority over competing Material state shadows. The target cannot clip, mask or draw over that ring. This preserves the visual relationship between focus and the actual visible control rather than implying a larger painted button.
- The design-system objective is a contiguous, independently operable 44 × 44 CSS-pixel square for each enabled target, not merely visual size. [WCAG 2.2 SC 2.5.5 Target Size (Enhanced)](https://www.w3.org/TR/WCAG22/#target-size-enhanced) is AAA and specifies 44 × 44 CSS px with stated exceptions; [SC 2.5.8 Target Size (Minimum)](https://www.w3.org/TR/WCAG22/#target-size-minimum) is AA and specifies 24 × 24 CSS px or its specified spacing/other exceptions. The proposed 44px target is stronger than the AA minimum; neither a token value nor this draft alone establishes WCAG conformance. Test actual target geometry, adjacent targets, keyboard, focus and AT in context.
- Scope is an unobstructed, unscaled, supported host with tokens resolving to a sufficient size. Clipping, overlays, ancestor transforms and locally overridden spacing tokens can reduce the effective target; the consumer must avoid or correct them. Do not claim a universal 44px guarantee under arbitrary overrides.

## 6. Appearance

No intended visible change to any preset, `outline` roundness, glyph, resting/hover/active/disabled appearance, Material layers, border, shadow, focus ring or reduced-motion behavior. Preserve the approved v0.2 no-hover-motion rule and the existing v0.3 outline hover-border decision; do not move Material paint to the hit-area element or invent a new recipe. Focus stays on the visible root. Dynamic inline geometry: **not proposed**.

**Tokens.** `packages/tokens/src/theme.css:460,595` provides `--space-14: 44.8px` and its `--spacing-14` utility alias; this already exceeds 44 CSS px, so no new token or dependency is proposed. The source explicitly allows local spacing overrides (`theme.css:565-567`), so a host overriding it below the required effective dimension must not be presented as satisfying the target. The `--space-16` fallback is 51.2px (`theme.css:462`), not an exact 44px token. Any future missing token or geometry exception needs separate confirmation; do not change token source or compiled artifacts in this amendment.

**Files / styling role.** The existing six roles remain: `types.ts` API/CVA, `useIconButton.ts` derivation, `IconButton.tsx` JSX, `IconButton.test.tsx`, `IconButton.stories.tsx`, and `index.ts`. Prefer static token-backed utilities and **No stylesheet**; a meaningful stylesheet role, new internal module, changed class composition or dependency needs its own explicit spec/plan approval. Preserve legacy styles. Static utility scanning, actual built CSS and a packaged consumer without its own Tailwind compiler must be checked by the implementation plan.

### Open human decisions

1. **Enablement:** recommend automatic for all enabled IconButtons, with no prop; alternatively approve opt-in `extendHitArea?: boolean = false` and explicitly narrow the current universal promise, or approve a default-true opt-out and its exception. The latter two require separate naming-convention review.
2. **Pointer policy:** recommend always for all pointers; alternatively choose `(pointer: coarse)` with its hybrid limitation or `(any-pointer: coarse)` with fine-pointer interception on hybrids. Review existing dense consumers and the overlap impact before adoption.
3. **Geometry / press feasibility:** recommend `--space-14` (44.8px) with an effective ≥44px square throughout press/release and no visible feedback change. If the separately reviewed plan cannot prove that, choose a compliant solution, including whether to accept a larger `--space-16` target and its spacing/press-edge impact, or separately approve a change to active feedback. No fallback, stylesheet or geometry exception is approved here.
4. **Visual source and adoption:** authorize the exact source, scenarios, conditions and read-only capture route for VIS-03; approve the resulting visuals separately. Confirm the historical references' intended limits for unchanged appearance.
