## 1. Purpose and scope

**Proposal.** Independently opt a `DialogContent variant="sheet"` into filling its layout boundary's width, limiting a long title, and rendering the existing supplied actions in a top area while the body is the normal scroll region. The existing capped sheet, unbounded header and footer actions remain the defaults. The three choices are independent: none implies another or changes a centered dialog. All exact API and fallback choices below remain open for the owner.

**Request and boundaries.** #539 describes Recado's 440px-wide Tauri floating panel; its triage accepted the request and split it into #543 and [#544](https://github.com/egdev6/egdev-design-system/issues/544). A ready positioned `container` and container-scoped overlay already exist. Nested confirmations above sheet chrome and locking dismissal during a pending action belong to #544, not this amendment. A controlled Dialog can currently decline a close request, but that does not disable its built-in close button. Do not promise either #544 behavior here. #539 remains the parent until both follow-ups ship in a release.

The supplied task reports Recado's `.panel-sheet` `max-width: none` override as DS046 and its `.panel-sheet > footer` workaround as DS047. The consumer CSS was not inspected here; these are reported context, not freshly verified findings. Recado #41 records issue-backed guard mitigations. Keep each TODO and allowlist entry until its complete corresponding need has shipped, the consumer has upgraded and its own checks verify removal. This draft neither changes the guard nor declares #539 or #41 resolved.

**Cataloging.** Reuse and amend the exported `@egdev/ui` Dialog molecule (`packages/ui/src/index.ts:63`, `packages/ui/src/molecules/dialog/index.ts`). Existing host composition alone does not remove the sheet cap, relocate the owned footer, or bound the title. A consumer CSS override reaches reserved width or internal structure, rather than expressing a supported component contract. A separate component or a new sheet variant would duplicate the modal and conflate independent layout axes; extraction is not needed. Radix Dialog, Surface, IconButton and consumer-supplied actions remain the existing pieces.

**Inspected baseline, not proposed behavior:** `packages/ui/src/molecules/dialog/types.ts:44-47,120-132,138-162` disallows sheet `size`, caps it at `calc(var(--space-24)*4)`, gives the panel clipped overflow, makes the header non-shrinking and gives the body `min-h-0 overflow-y-auto`. `Dialog.tsx:35-61` renders the title and optional description/status in the header, actions in a bottom `footer`, and the built-in close last in panel DOM. `useDialog.ts` derives the viewport/container scope and ignores centered sizes for sheets. None of this source inspection measures actual geometry or proves the proposed layout.

## 2. Anatomy and composition

| Part | Existing responsibility | Proposed sheet-only delta |
| --- | --- | --- |
| Root, Trigger, Portal, Overlay | Radix modal, trigger and internally owned portal; overlay grid is viewport- or container-scoped | Unchanged interaction and scope. The overlay is the width boundary, not necessarily the portal mount node. |
| Panel | Radix Content rendered through Surface, full height at logical inline-end | Optional full boundary width; keep sheet Material and RTL-aware edge/motion. |
| Header, title, description, status | Native header, Radix Title and optional Description, passive status; built-in Close is separately positioned | Optional two-line title clamp; preserve full title text and relationships. Existing inline/stacked title-description arrangement remains available. |
| Top actions | Consumer `actions` ReactNode, currently rendered only in the footer | On `actionsPlacement="header"`, render that same content exactly once in a dedicated row inside the header after the title/description group, before the body. It is not a new slot, menu, toolbar or landmark. |
| Body and default footer | Body owns native vertical scrolling; existing footer holds actions when non-null | Body remains the normal scroll region. Omitted/`footer` placement preserves the existing footer, order and treatment. |
| Built-in close | Radix Close asChild wrapping a ghost `lg` IconButton, last in DOM | Remains separately positioned and last in DOM; reserve its complete target and focus ring beside the top area. |

Keep `eg-dialog-backdrop`, `eg-dialog`, `eg-dialog__head`, `eg-dialog__title`, `eg-dialog__description`, `eg-dialog__status`, `eg-dialog__body` and the existing `eg-dialog__foot` action-part marker. The recommended top row is a non-landmark `div` retaining `eg-dialog__foot`; default placement retains the existing `footer` element and marker. Thus an opted-in top row changes the actions' DOM location and element, while existing calls do not. A retained marker is not permission for consumer descendant selectors. The proposed row must override any conflicting legacy foot styling through approved component recipes without altering legacy rules. Radix keeps its own Portal and `asChild` composition; no new primitive or focus engine is proposed.

## 3. Public API

The following is the **recommended candidate**, not an approved API. Each new option is sheet-only. A proposed discriminated type preserves centered `size?: DialogSize` and accepts, on the `variant: 'sheet'` branch only:

| Prop | Candidate type / default | Proposed rule |
| --- | --- | --- |
| `size` | `size?: 'full'`; omitted means existing capped sheet | `'full'` fills the overlay's available inline width. Omission remains capped; `sm`, `md` and `lg` remain invalid on sheets. Centered `sm/md/lg/full` and centered default `md` do not change. |
| `titleOverflow` | `'default' \| 'clamp'`; default `'default'` | `'clamp'` limits the visible title to two lines, preserving its complete string. The consumer supplies the visible full-title route in §5. `'default'` keeps existing behavior exactly. |
| `actionsPlacement` | `'footer' \| 'header'`; default `'footer'` | `'header'` moves the existing `actions` content to the dedicated top row. Render it once, preserve its own handlers and order, and do not create a footer for it. `'footer'` retains the existing rendering. |

The centered branch would declare `titleOverflow?: never` and `actionsPlacement?: never`; it continues to accept the current `size` type. Sheet `size='full'`, the title limit and top actions can each be selected independently or combined. For untyped inputs, unsupported sheet size values retain the capped sheet, unknown title/placement values use their existing defaults, and centered layout ignores the sheet-only options; none of these options is forwarded as a DOM attribute. The existing nullish test for `actions` remains: only `null`/`undefined` omit the actions part; do not silently change how other ReactNode values are handled.

Existing `title: string`, `description?: string`, `statusText?: string`, `children: ReactNode`, `actions?: ReactNode`, `dismissLabel`, `headerLayout`, `bodyPadding`, `container` and `overlayScope` retain their types and ownership. The actual title is non-empty and localized. Inherited native Content props, its exclusions, lack of a Content ref or `asChild`, Trigger/Close refs, controlled/uncontrolled open state, exports and supported `className` boundary remain unchanged. No event, built-in action, pending state or new modal scope is proposed. Top placement changes Tab order to follow actual DOM order: supplied top actions, then body controls, then the built-in close, subject to Radix's initial-focus behavior.

**Prop naming lookup.** Consulted the [registry source](../../../../skills/_shared/prop-naming.json), [generated view](../../../prop-naming.md) and [meaning/name/alias workflow](../../../../skills/_shared/component-contract.md#prop-naming-registry):

- Reuse approved `preset-dimensions` → `size` for the extended sheet-specific `'full'` type; `visual-treatment` → `variant`, `trailing-actions` → `actions`, `dialog-header-layout` → `headerLayout`, `portal-container` → `container` and `dialog-overlay-scope` → `overlayScope` retain their existing meanings. `host-fill` / `fill` concerns block-axis height, not panel width.
- The approved `tab-list-full-width` → `fullWidth` explicitly describes equal distribution of segmented tabs and avoids arbitrary element width. A sheet boolean named `fullWidth` cannot be silently treated as that usage; it would require a reviewed convention change or other explicitly approved naming resolution. `top-bar-content-width` describes an inner row with gutters, not this panel's boundary.
- Propose **new** semantic ID `dialog-title-overflow`, name `titleOverflow`, component-specific type `'default' | 'clamp'`: a sheet's visible owned title is either unchanged or limited to two lines without changing the string. Approved `single-line-text-truncation` / `truncate` explicitly excludes multi-line clamping; `control-label-wrap` concerns control labels, not this title.
- Propose **new** semantic ID `dialog-action-placement`, name `actionsPlacement`, component-specific type `'footer' | 'header'`: select where this Dialog renders its existing actions. It is not `floating-side`, `icon-placement` or a new actions slot. Neither proposed entry has an approval or scoped exception; semantic and naming approval are separate from spec approval.

Reviewed existing source: `{path: 'packages/ui/src/molecules/dialog/types.ts', symbol: 'DialogContentProps', revision: 'sha256:631f34f582959c9049124289bc570686e0505fe03d099fb83ee18403e37d8479'}`. This identifies the existing symbol and **does not** assert that either proposed prop is implemented. After a separately authorized source change, review the final symbol and whole-file hash, update any affected existing registry usages and approved new entries, and regenerate the view; this draft changes neither registry nor generated documentation.

**Recado-shaped composition, conditional on approval:**

```tsx
<DialogContent
  variant='sheet'
  container={host}
  overlayScope='container'
  size='full'
  title={entryTitle}
  titleOverflow='clamp'
  actionsPlacement='header'
  actions={<Button labelWrap={true} onClick={onApply}>Apply changes</Button>}
>
  <p>{entryTitle}</p>
  {content}
</DialogContent>
```

Here `host` is a ready, connected, positioned, non-scrolling same-document element of adequate size; the consumer supplies `entryTitle`, `content` and the `onApply` action handler. The full title is visibly available at the start of the body as well as remaining the dialog's accessible name. This is a proposed example, not verified Recado code. The consumer owns the complete-title route and must not rely on `title` or a tooltip alone.

## 4. Behavior

| Given / action | Proposed result |
| --- | --- |
| No new options, or explicit defaults | The capped sheet, existing header behavior, footer actions, markup, defaults, interaction and supported layout remain unchanged. Centered dialogs are unaffected. |
| Sheet `size='full'`, container-scoped overlay | The panel's border box fills the overlay content box inline, without the existing max-width cap or horizontal overflow. The overlay is inset to the positioned host's padding box; the host border is not part of the sheet width. Resize the host and the panel follows without measurement. |
| Sheet `size='full'`, viewport-scoped overlay | Fill the viewport-scoped overlay, even when the portal mounts under a custom `container`. Mount target and layout boundary are not interchangeable. Existing ancestor clipping and fixed-containing-block restrictions apply. |
| Sheet `titleOverflow='clamp'` with fitting or long title | Keep the complete title in the Radix Title DOM node. Render at most two visible lines; long words may break, and overflowing text receives visual ellipsis. No title string slicing, tooltip, new focus stop or disclosure is generated. |
| Sheet `actionsPlacement='header'`, actions supplied | Render actions once in the top row above the body; they remain visible while the body scrolls in the supported host conditions below. Preserve their own native semantics, callbacks, order and disabled state. |
| Empty/short body or absent actions | The body remains present; null/undefined actions add no actions row or footer. A short body does not need a scrollbar. Existing non-nullish ReactNode handling is preserved. |
| Open, dismiss, resize, switch supported inputs | Radix retains state and dismissal; layout changes do not emit an open-change event. Focused controls and full content remain reachable; no action is duplicated or automatically activated. |

**Space and overflow constraints.** The normal guarantee requires a host wide and tall enough for the complete top chrome, unobstructed targets, and a body **content box** at least `--space-14` high after body padding (44.8 CSS px with default tokens). Header metadata and consumer actions must themselves fit that chrome; the API accepts arbitrary `ReactNode`, so an unlimited action collection or unlimited description/status cannot be guaranteed to fit an arbitrarily small host. Actions may wrap without overlap; consumers choose a manageable set and provide an adequately sized host. When `titleOverflow='clamp'` is selected and those preconditions hold, an arbitrarily long `title` alone cannot consume the body: its visible title is at most two lines, the body has the stated minimum and the body is the only scrolling area. Top actions alone do not bound the title; select the clamp independently when that protection is needed. Both `inline` and `stacked` arrangements must be checked, including long unbroken strings and both body-padding presets.

At extreme zoom or in an insufficient host, keeping all actions permanently visible, arbitrary amounts of header/action content and a nonzero body in an arbitrarily small host, with **only** body scrolling, is mathematically impossible. The recommended emergency fallback is to let the existing overlay scroll only in sheets opting into `titleOverflow='clamp'` or `actionsPlacement='header'`, and only when the required chrome plus minimum body cannot fit, rather than clip a focusable control; that exception can move top actions out of view and therefore needs the explicit owner decision in §7. It is not presented as satisfying the unconditional 'only body scrolls' request. Until that decision is resolved, the proposal is not implementation-ready.

The existing host lifecycle, viewport-scope restrictions and document-wide Radix modality from v0.2 remain. Do not promise nested dialogs, local-only modality, automatic host resizing, arbitrary content fitting, data loading or a dismissal lock.

## 5. Accessibility

Keep Radix's dialog role, modal semantics, generated title/description relationships, initial-focus algorithm, focus trap, Tab/Shift+Tab, Escape, outside dismissal and Trigger restoration. Because top actions precede body controls in DOM, Radix may initially focus the first top action instead of a body control; the exact initial target is intentionally not promised unchanged for this opt-in. Default placement retains its existing focus order. A trigger-less controlled consumer still owns restoration. The header's visible clamp must not remove, replace or `aria-hidden` the original complete Radix Title; `aria-labelledby` continues to name the dialog with the full string. Optional Description retains its existing relationship; status stays passive and is not an invented live region. No layout option itself changes announcements.

Visual ellipsis is not a full-text access mechanism. For `titleOverflow='clamp'`, the consumer must provide an always discoverable visual route usable by pointer, keyboard and touch that exposes the **complete** title, for example its full text at the start of the scrollable body. If content is duplicated, the consumer handles any unnecessary duplicate announcement without hiding or altering the Radix title. A native `title` attribute or Tooltip is supplementary only; neither supplies a reliable keyboard-and-touch route. Consumers own the names, focus visibility and action semantics of supplied controls. Do not clip interactive descendants or their focus rings to enforce a title bound.

**IconButton 0.8.0 interaction.** The close's visible `lg` box is 38.4px at default tokens, but its automatic centered all-pointer `--space-14` hit square is 44.8px, extending 3.2px past each visible edge (`packages/ui/src/atoms/icon-button/types.ts:28-32,56`; [implementation evidence](../../icon-button/v0.4/implementation-evidence.md)). Reserve that entire unclipped square and the visible-root focus ring, and test actual pointer-down/up/click, not just visible boxes. For adjacent IconButtons with overlapping cross-axis ranges, reserve a visible gap **at least one spacing token above the sum of their target outsets**: with default tokens and the `lg` close, `sm/lg` needs `gap-5`, `md/lg` needs `gap-4`, and `lg/lg` needs `gap-3`. This margin is stronger than merely touching the hit squares. Apply the same outset-plus-margin principle to other adjacent interactive targets, wrapped rows and RTL; because the close is absolutely positioned, a flex `gap` alone does not prove clearance. Do not suppress its extension using the separate ButtonGroup/Tabs compact exceptions. Token overrides, clipping, stacking and transformed ancestors can invalidate these dimensions; verify the actual host and both input types. No unconditional WCAG conformance is claimed.

## 6. Appearance

| Axis | Proposed opt-in | Preserved / restriction |
| --- | --- | --- |
| Width | `size='full'` removes only the sheet's width cap and fills its overlay boundary | Omitted sheet remains capped and inline-end; centered sizes are unchanged. No consumer width override or arbitrary numeric width. |
| Title | `titleOverflow='clamp'` visibly limits only the title to two lines | Keep typography, text content, direction, existing inline/stacked relationships and v0.3 first-line close alignment / last-visible-line metadata alignment where applicable. Verify real baseline geometry, not just classes. |
| Action area | `actionsPlacement='header'` uses a separate top row with the existing sheet footer's `surface-1` tone and hairline semantics | Default footer remains unchanged. No extra action paint, independent scrolling row, new shadow, or duplicated actions. The top treatment is a component-specific proposal pending owner review. |
| Normal scrolling | Header and actions remain visible; body alone scrolls | Emergency overlay fallback is an unresolved exception, not an implicit default change. |

Surface continues to own sheet overlay paint, including solid reduced-transparency and unsupported-filter fallback. Preserve the scrim, existing focus priority, reduced-motion behavior, title/description typography, logical direction and existing token-backed Material; do not copy Surface classes or invent colors, gradients or shadows. The proposed action band reuses existing sheet footer semantics, not a new unapproved Material recipe. If its placement requires a different band or separator, obtain explicit owner approval. No new token, dependency, inline appearance, measured dynamic geometry or class-string interpolation is proposed.

Retain six meaningful roles: `types.ts` owns props/static CVA; `useDialog.ts` derives layout and `cn()` compositions; `Dialog.tsx` renders JSX; `Dialog.test.tsx` and `Dialog.stories.tsx` cover behavior/examples; `index.ts` exports the public API. **No stylesheet** or extra internal module is proposed. Preserve shared marker-free scrim/panel helpers and verify any change against AlertDialog and CommandPalette; do not assume a Dialog-only change cannot affect siblings. Keep legacy CSS intact. Content `className` remains supported outer-layout composition only: overrides of width, padding, radius, paint, focus or positioning remain unsupported even if the cascade permits them. `cn()`/`twMerge` are not a universal cascade or policy guarantee; no DS046 allowance or DS047 exception is added.

### Open owner decisions

1. **D1 — Full width API.** **Recommend** allowing `size='full'` only on sheets, with omitted sheet size still capped; reuse `preset-dimensions` and preserve centered sizes. Alternative: a separate boolean such as `fullWidth`, default false; it is more explicit but needs the naming-registry resolution described in §3 and another axis. Neither option approves arbitrary width overrides.
2. **D2 — Long title and visual access.** **Recommend** sheet-only `titleOverflow='default' | 'clamp'`, default unchanged; `'clamp'` means at most two visible lines with the full title retained in the Radix node and a consumer-provided visible route. Alternatives: a single-line truncation with the same route, or scroll/move the heading instead of clamping. The latter either adds a scroll region or changes reading/layout ownership and must not be represented as the same contract. Approve the line limit, naming and full-text route explicitly.
3. **D3 — Top action API and structure.** **Recommend** `actionsPlacement='footer' | 'header'`, default footer, moving the existing `actions` once into a dedicated header row and retaining the public actions marker. Alternatives: a new sheet variant coupling width/header/actions, or a separate new top-actions slot alongside the footer; these create coupled choices or permit duplicate actions. Approve the opt-in DOM/Tab-order change and top-row element/treatment.
4. **D4 — Insufficient host.** **Recommend** exceptional overlay scrolling only for sheets opting into the title clamp or header actions when fixed chrome plus the minimum body cannot fit, so focusable controls are not clipped; document that top actions may then scroll and that this is an exception to #543's only-body-scroll outcome. Alternative: require a sufficiently large host and leave smaller hosts unsupported, with the consumer responsible for adapting before opening. The owner must choose this tradeoff; neither accessibility nor the original unconditional wording can be satisfied for arbitrary content in an arbitrarily small host.
5. **D5 — Material and visuals.** **Recommend** reusing the existing sheet footer's `surface-1` band and hairline semantics for the top row, with no new tokens or handwritten paint. Alternative: approve a distinct Surface-composed top treatment and its exact recipe. Decide whether to approve the spec without new captures or first supply and adopt VIS-01–03; visual conformity remains Not evaluated without comparable approved references.

**Next step:** resolve D1–D5 and both proposed naming conventions, finalize any resulting new snapshot and obtain exact-snapshot owner approval. Then propose a separately approved implementation plan, including browser, accessibility, packed-consumer and Recado verification. This draft authorizes no code, token, dependency, registry, capture, release or external mutation.
