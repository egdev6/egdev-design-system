## Recommendation and dependency decision

Recommend the contract's **Move-menu-only fallback** for v0.1: it provides both keyboard and pointer/touch moves without a new drag library and avoids competing focus and gesture models. This requires explicit owner selection at the plan gate; no spec amendment is needed for this specified fallback. No dragging, drag overlay, drop-target state or dragging presentation ships in that branch. AC-09 is conditional on choosing drag; AC-10 and all other applicable criteria remain mandatory.

The issue recommends `@dnd-kit/core` as an optional pointer shortcut. It is a credible purpose-built alternative, not a Radix grid primitive, but is **not recommended in this plan** and is not installed. If the owner chooses it instead, select an exact version and obtain separate dependency approval before installation; revisit the plan and test AC-09. Its contract requires PointerSensor distance 8px, TouchSensor delay 250ms/tolerance 5px, no KeyboardSensor, no draggable role/tabindex attributes on the `li`, a portalled overlay, and reduced-motion drop animation disabled. The menu remains mandatory. Test link/menu click versus drag and touch scrolling; no own-day, outside, non-accepting or cancelled drop may emit a move. No sortable package is needed.

There is no Radix ARIA grid primitive, but the approved D6 explicitly chooses **no ARIA grid** rather than a custom roving-focus 2D grid. Native lists and buttons plus Radix DropdownMenu through Menu supply the actual model. Thus there is no arrow-key grid implementation and no conflict with the rule against reimplementing existing Radix keyboard/focus/ARIA. A future ARIA grid would change the contract and require its own design and approval. `@radix-ui/react-dropdown-menu@2.2.1` and `@radix-ui/react-visually-hidden@1.2.13` are already direct dependencies according to `packages/ui/package.json`; the issue's older absence statement is historical. No new Radix or date dependency is proposed.

## Public API, data and conventions

The complete #126 API is authoritative. Required `label: string` names the section; `items: CalendarGridDay[]` is in consumer order. Day fields are `date`, full `label`, `weekday`, `dayNumber`, `entries`, optional `'aria-current': 'date'`, `past` and `acceptsEntries`. Entry fields are globally unique `id`, `label`, optional `meta`, `href`, `status` (`default | new | failed | done | off`) and `movable`. Non-default statuses require a readable word in `meta`. The actual entry footer places meta **below** the label (D9/AC-06), despite a stale type-comment saying above.

`onAdd(date)` and `onMove(entry, date)` are requests, never mutations. `onNavigate(entry, React.MouseEvent<HTMLAnchorElement>)` permits router interception while preserving native anchor behavior. `level` is 2–6, default 3; `messages` supplies localizable text/formatters with per-field English fallbacks. There are no `view`, `variant`, `size`, `tone`, `asChild` or ref APIs. Forward compatible section props, omitting `children`, `role`, `aria-label` and `aria-labelledby`; `className` supports outer layout only. Use `ComponentPropsWithoutRef`, `type`, no `any`; apply owned semantics after rest forwarding.

Dates are consumer-provided valid unique ISO calendar-date strings (`YYYY-MM-DD`) and opaque keys/payloads, not `Date` instances: no date parsing, `Intl`, arithmetic, timezone conversion, sorting, locale or week-start computation. Consumers own these, past/today and eligibility, conflict rules, persistence and optimistic updates. Support 1–7 days; the explicitly specified empty-input behavior is a named region with an empty list, not fabricated days. Do not invent behavior for other invalid input.

Naming maps `label` → `accessible-name`, `items` → `collection-items`, `onNavigate` → `navigation-intent`, `level` → `heading-level`, `messages` → `localized-messages`, and entry `status` → `item-presentation-status`. The issue's new-concept candidates `onAdd` → `add-request` (shared with ModuleRail) and `onMove` → `move-intent` already appear as **approved** in the current canonical `skills/_shared/prop-naming.json`, with the organism delegation receipt and empty usage lists; that receipt is assistant-applied acceptance under human delegation, not independent native review. Do not duplicate them or treat this plan as fresh convention approval. `collection-items` currently says molecule in its usage guidance; confirm organism applicability under the issue's explicit mapping rather than silently widening the registry. At implementation, review `CalendarGridProps` source and append usages with the real whole-file SHA-256; regenerate and validate the registry only with authorized scope. Native attributes and component data fields are not extra root-prop conventions.

## Behavior and accessibility

- Native Tab/Shift+Tab visits each entry link, its move trigger, then the day's add button in data order. Headings and lists support screen-reader navigation; no `grid` or `gridcell` roles. Named heading contains the full day label and localized Today; visible abbreviated weekday/number are hidden from assistive technology. Only today's day gets `aria-current="date"`; `past` mutes header numerals, not entry content.
- When `onAdd` exists, each accepting day has a native `type="button"`, 44px minimum height, decorative plus and accessible `messages.addEntry(day.label)`. Click, Enter or Space emits that day's date once; no handler or `acceptsEntries: false` means no button. Empty days expose `messages.noEntries` and no entry `ul`.
- When `onMove` exists, movable entries with at least one other accepting day have a named trigger. Menu has `messages.moveTo` and one action per eligible other day, labelled by full day label. Radix provides arrow keys, Home/End, typeahead, Enter, Escape and focus return; select emits the original entry and target date once, without moving it locally. No target, `movable: false` or absent handler means no trigger.
- Track the last requested `(entryId, targetDate)`. When subsequent props place that entry in that target, focus its remounted move trigger and announce `messages.entryMoved(entry.label, day.label)` once in a polite hidden `role="status"`. Rejected/unchanged data generates no announcement and Menu returns focus to the original trigger. Ordinary unrelated prop updates do not announce. The API has no explicit rejection signal; resolve pending lifecycle and a missing target trigger with the owner before coding (below), not by claiming an arbitrary timer is contract behavior.
- Link labels remain native anchors only when `href` is present; `onNavigate` may call `preventDefault`. Entry containers never become links/buttons. Status is not conveyed by color alone; add and move controls are independently named. Check screen-reader behavior, contrast, zoom, touch and focus visibly in a browser; unit tests do not certify accessibility.

## Risks and owner questions before implementation

1. **Branch decision:** approve this menu-only plan (no new dependencies), or request the issue's dnd-kit pointer shortcut with a separately approved exact version and updated plan? Both retain the keyboard-accessible menu.
2. **Focus after acknowledged move:** D15 promises focus on the moved entry's trigger, while D13/AC-07 removes that trigger when no other accepting day exists or `movable` becomes false. Should a versioned clarification specify a fallback focus target in that case, or must the host preserve a trigger? Also clarify when a pending request expires after rejection or unrelated updates: the API supplies no rejection signal, so a later coincidental move to the same date could otherwise announce falsely. No silent amendment is proposed.
3. **Touch:** #126 records a 32px move-trigger exception even on narrow touch layouts; `IconButton` types require at least a 44px touch hit area. Confirm whether to retain the issue's exception or authorize a contract amendment for a ≥44px hit area on coarse pointers. Do not silently change `sm` to another size.
4. **Prerequisites:** confirm the integrated public ListItem/Menu/IconButton/Icon/VisuallyHidden APIs and plus glyph actually satisfy #126, including Menu's trigger ref/portal composition and ListItem's parts. If not, stop for a bounded prerequisite/contract decision rather than cloning or changing them.
5. **Naming scope:** confirm the approved `collection-items` convention applies to this organism despite molecule-specific `whenToUse` wording; do not silently alter global convention approval.

## Owner decisions (2026-11-02)

Recorded after the implementation raised three of the questions above as open. The owner choices are quoted verbatim; each question is closed.

1. **Focus after an acknowledged move without a target trigger** — owner choice: “Encabezado del día destino (Recomendado)”. When the moved entry's Move trigger no longer exists after the consumer update, focus moves to the destination day's heading as an internal fallback: no public API change and focus is never left on `body`. The heading is programmatically focusable with `tabIndex={-1}` so it stays out of the Tab order. The one-shot polite announcement of the applied move is unchanged. Behavior-level coverage: `CalendarGrid.test.tsx` “falls back to the destination day heading when the moved entry has no move trigger” (RED before the change: focus stayed on `body`).
2. **Move trigger size** — owner choice: “Mantener la excepción (Recomendado)”. The contract's recorded 32px `IconButton` `sm` exception stands, including on narrow touch layouts; no size, token or contract change. Only the accepted exception is recorded here.
3. **`collection-items` for organisms** — owner choice: “Aprobar para organismos (Recomendado)”. This is an explicit convention approval extending `collection-items` applicability to organisms, recorded as a separate amendment with an appended receipt and superseded wording: [collection-items-organism-amendment.md](collection-items-organism-amendment.md) and [collection-items-organism-approval.json](collection-items-organism-approval.json). ## Owner decision: responsive stacking token (2026-11-02)

Browser check of the committed branch found the `@4xl` container fallback in D17 generates no CSS (`--container-4xl` is not defined in `theme.css`), so the lanes never stacked. Owner choice, verbatim: “Agregar --container-calendar-grid-stack: 960px (Recomendado)”.

- **Token:** `--container-calendar-grid-stack: 960px` is declared once in `packages/tokens/src/theme.css`, next to `--container-quote-pull`, with a one-line comment citing #126 D17 and recording that it is unscaled like the other breakpoints. `packages/ui/src/styles/compiled.css` already scans this component's `types.ts`, and the tokens `dist/` artifact is never hand-edited.
- **Utilities:** every `@max-4xl:` in `packages/ui/src/organisms/calendar-grid/types.ts` is now `@max-calendar-grid-stack:` (day list `grid-flow-row`/`grid-cols-1`, lane `min-h-0`). The 56rem Tailwind default is no longer used; the 960px component container size replaces it and D17's threshold is unchanged in intent.
- **Coverage:** behavior-level class contract in `CalendarGrid.test.tsx` (“stacks the lanes from the component container token instead of an undefined breakpoint”, RED first on `@max-4xl:`) and a tokens assertion in `packages/tokens/tests/token-contract.test.mjs` (“theme.css declares the CalendarGrid stacking container size (#126 D17)”, RED first), with the pinned utility/total counts updated for exactly this one token (213 → 214 and 285 → 286).
- **Story:** the `MoveMenu` story is stateful (and only it): it keeps `items` in React state, applies the requested move, and keeps using the system components, so the moved entry renders in the destination day, the polite status region announces `entryMoved` and focus follows the contract.
