## 4. Findings

- **F1: the plan's derived-load mechanism reports a stale `ready` (fixed, test-first).** The plan's `loadedSource` plus `key={src}` records the exact `src` that loaded, so a `src` that comes back keeps its old record: A, then no `src` or B, then A again showed `ready`, no Spinner and no `aria-busy` for a fresh, unloaded frame. Two tests pin it (R4b). The fix is the documented React pattern of adjusting state during render: a second state records the tracked frame source and the load record is dropped in the same render when it changes, so there is still no effect and no public API change. Verified in a real browser with a held request (section 3).
- **F2: two expectations of the plan's artifact and catalog wording were corrected in my tests, not in the component.** The artifact prints an enum prop by its docgen type (`enum`), and the catalog keeps a multi-part cell as one entry (`["Spinner, Surface recipe"]`, like `Menu`'s `["Icon, Kbd, Surface recipe"]`).
- **F3: the plan's fixture import is inlined as a `data:` URL in the production Storybook build.** The 2,202-byte `diagnostic.svg` is below Vite's 4,096-byte inline limit, so `?url` produced `data:image/svg+xml;base64,…`, which Embed rejects by design (EM-08): `Default` and `Ratios` would have rendered the empty fallback. The stories import the same file with `?no-inline` (typed in `vite/client`), so it is always a same-origin `/assets/…svg` URL. D5 stands (same file, no new file); the plan's risk list did not foresee this.
- **F4 (stop line, resolved by Amendment 1): the fallback layer was not centered without a border-box reset.** Plan G4 and section 14 say to stop when computed style disagrees with the spec's block 6. The recipe was exactly the approved one (`grid size-full place-items-center p-6 text-center font-sans text-body-default text-fg-muted`), and the Spinner layer and the frame were unaffected. Without Tailwind's preflight (this Storybook, native-CSS consumers, the packed no-compiler path) the layer overflowed the box by twice the padding and was clipped by the well; a consumer with preflight (the website) got the intended geometry. No fix was made in the first run, because every fix changes the approved utility inventory, and the owner was offered three choices: **(A, recommended)** add the existing static utility `box-border` to `embedFallbackVariants` (Surface and Pagination already use it; it is a keyword, not a value or token); **(B)** drop `p-6`, so the layer is exactly the box and the consumer pads its own content; **(C)** ship as is and document a preflight dependency. **Resolution:** the owner chose A, verbatim "A: agregar `box-border` (Recomendado)" (`odd/tasks/round-5-consumer-requests.md` L8). The spec's fallback recipe was amended ([`approval.md`](approval.md) Amendment 1, spec digest `a0041443…` to `11b93680…`, plan header re-pinned with a re-approval note, plan payload unchanged), `box-border` was added as the first utility of `embedFallbackVariants`, and the freshness chain was run (section 7). jsdom has no layout, so no unit test can assert the geometry; a recipe guard (any part that is full-size and padded must be border-box), assertions on the server markup of the built and the packed package, and the browser A/B of section 7 cover it instead.
- **F5: VIS-03, on a solid `surface-0` host the well separates only by its hairline.** See section 3. This is a spec question under G5, not a failure; a different tone would need a separate approved proposal and none was improvised.
