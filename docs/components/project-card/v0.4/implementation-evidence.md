## 4. Findings

None of these needed a code or spec change, and none was acted on.

- **F1 — The artifact differs in four strings, not two (G8, spec V-12).** Measured against the artifact of the starting tree, which R0 proved fresh, the regenerated `design-system.json` differs in `components[ProjectCard].parts[ProjectCardFooter]` `description` and `children` (the two the plan expected) and also in `components[ProjectCardFooter].props[children].description` and `components[ProjectCardFooter].variants[projectCardFootVariants].classes[0]`, whose literal gains `flex-wrap`. V-12 looked at ProjectCard's own `variants` and `anatomy` and missed the top-level `ProjectCardFooter` component entry, which the artifact publishes with its props and recipe. `system.md` changes one line. The artifact stays 647,173 bytes against the 786,432 budget. **Parent decision A (not an owner approval), 2026-11-27:** accept as generated, because the two extra differences are the deterministic result of the approved JSDoc and recipe change and no promise changes; the spec and plan stay untouched. The system changelog entry follows the artifact: it says the recipe lists `flex-wrap`, where plan section 7 said "the existing props and recipes are unchanged".
- **F2 — The spec's narrow examples do not force a wrap.** PC-F4 reads "with three realistic actions in a `w-72` host and at a 320px viewport, the later actions flow onto further lines". With the story's labels (`Details`, `GitHub`, `Demo`) the row is 180.97px and a 288px card has 247.6px of content, so those two examples stay on one row (section 3); the wrap starts below a 222px card or with longer labels. The footer wraps whenever the row does not fit and no recipe addition was needed, so G8's "overflows instead of wrapping" did not hold; the observation is about the examples. Before any VIS-02 capture is authorized, its condition (the spec proposes `WithActions` at a 320 × 800 viewport) needs a host of about 220px or less, or longer labels, or it will show a single row.
- **F3 — The Docs page has no `ProjectCardFooter` row.** Plan section 9.6 expects "the docs row for `ProjectCardFooter` `children`", but a part's props are not tabulated on the `ProjectCard` Docs page, so that row cannot be observed in a browser. The new `children` description is verified through the real docgen extraction (the PC-10 case) and the artifact test (D3), and the Docs page does show the new story and text.
- **F4 — The plan's `WithLink` description trips its own search.** Plan section 6 gives "A footer with a single action; the card itself adds no tab stop.", and the section 8 search for `single action` must print nothing, so the two cannot both hold. The description reads "A footer with one action; the card itself adds no tab stop." No promise changes.
- **F5 — Stacked Links miss the 24px spacing by 0.96px.** In a card narrow enough to stack the two Links on separate lines (below about 156px of card width: it first showed at the 140px host, while 160px still keeps them on one line), the Link boxes are 13.44px high and the 9.6px gap leaves their centres 23.04px apart, so the spacing exception of WCAG 2.5.8 does not hold by the calculation of section 3. In every observed card from 160px up, including the 1280, 640 and 320px viewports, it holds. The Link height belongs to the Link atom and the label wording to the consumer, so this is recorded and not changed.
