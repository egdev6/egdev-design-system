## Amendment 1 — F4: the inline-code selector reads `code:not(pre code)` (2026-11-27)

The amended payload hash below is the current one. The SHA256 at the top of this record stays as the hash the original approval bound.

- **Date:** 2026-11-27
- **Reason (finding F4):** the real-browser check of the #569 implementation (ODD S4, task T6: Chrome for Testing 153 on the static Storybook build and on bare consumer pages; [implementation-evidence.md](implementation-evidence.md), finding F4) found that the approved inline-code selector `:not(pre) > code` does not reach a `code` that is a direct child of the root. The root is not a descendant of itself, so `<Prose><code>x</code></Prose>` kept the mono 11.2px face but inherited the host colour (`rgb(255, 255, 255)`), while a `code` inside `p` was neon and `pre > code` was block-coloured. The same selector also coloured a `code` that sits deeper inside a `pre` (`pre > span > code`), because its parent is not a `pre`; the amended selector leaves that one out too. The implementation followed the spec's own spelling and reported the gap, together with F3 (the 65ch measure holds about 85 characters per line in Barlow).
- **Change:** the three passages that spell the selector, and nothing else in the payload: the "Inline `code` only" row of the block 6 recipe inventory; the selector list of PRS-04; and the promise and method of PRS-06 (a `code` that is a direct child of the root now computes the inline recipe, and the method adds a selector-match test over the root's own recipe variant). Header metadata above the hash anchor records the amendment (status, approval and recovery, and the `approvalReference` and `contentSHA256` identity fields). The block 1 compile evidence, which records what the original candidate utility set compiled to, stays as written.
  - Before: `:not(pre) > code`, the Tailwind variant `[&_:not(pre)>code]`.
  - After: `code:not(pre code)`, the Tailwind variant `[&_code:not(pre_code)]`: the smallest selector that matches inline code anywhere under the root except inside a `pre`. It is one `code` type selector plus one `:not()` whose argument is a complex selector, so its specificity is (0,1,3) against (0,1,2) before; no other rule sets the colour of a `code`, so no cascade outcome changes.
