## 4. Findings

- **F1: DH-11 holds for the approved fixture, but unbroken tokens overflow at narrow widths (needs the parent's reading).** The approved scenario (plan section 9.1: a long multi-word title, an unbroken 60-character value, a long link label, many tags) passes. A deliberately unbreakable fixture (an informational probe on separate pages) shows where the limit is, at a 320px viewport (272px content width in the consumer page): the unbroken 120-character fact value wraps (3 lines); an unbroken 90-character link label stays one 785px line inside its 272px item (`li` `scrollWidth` 785 over `clientWidth` 272); a single unbroken 80-character tag is a 425px nowrap Chip past the 296px root edge (Chip's own `white-space: nowrap`); and an unbroken 78-character title is a 1223px heading (1956px at 1280px) that overflows the page (document scroll 1247 and 1980), which is Heading's behavior and the SectionHeader finding that plan section 9.1 and Risk 2 anticipated, not a DetailHeader fix. I read DH-11's "long link labels" and block 4's "long values wrap" as covering multi-word labels and values, so I treat the unbroken label and tag as a limit, not a contradiction, and changed nothing. If the owner wants an unbroken link label covered, the additive remedy is `wrap-anywhere` on the link item recipe (`detailHeaderLinkItemVariants`), a spec amendment because block 6 lists that recipe as `min-w-0`; a single unbroken tag cannot be fixed inside DetailHeader. **Owner decision and fix (2026-11-27):** the owner chose that remedy, verbatim "Agregar `wrap-anywhere` (Recomendado)" (L8), and Amendment 1 added `wrap-anywhere` to the link item recipe: an unbroken link label now wraps (section 7). The measured reach is the link label only; the unbroken tag and the unbroken title are unchanged and stay outside DH-11.
- **F2: `gap-1.5` is token-derived, not a token step.** It serializes as `calc(var(--space-1) * 1.5)` in both CSS pipelines, as Chip and the ProjectCard tag list already ship it; the preview, built and packed CSS checks pin that form, and the first run of the preview check recorded it.
- **F3: Chromium reports the term and heading names in the rendered case.** The accessibility names read `DATE` and `OPEN SOURCE DESIGN SYSTEMS MEETUP` because the recipes uppercase them with CSS, while the DOM text equals the supplied label (unit-tested), as spec block 4 states. How a screen reader speaks them is **Not evaluated**.
- **F4: the nested `header` is a `banner` outside `main` and `article`, in Chromium 153.** Spec block 5 flagged this as unobserved; Chromium exposes SectionHeader's `header` as `banner` in a bare `div` and as `sectionheader` inside `article` or `main`. The stories wrap the header in an `article` through one meta decorator so they model the documented placement.
- **F5: the hook also drops `ref`.** React 19 hands `ref` to a function component as an ordinary prop, which would otherwise reach the root there and not under React 18; the spec says there is no public ref, so the hook strips it (as the Breadcrumb lane did) and a `createRef()` test proves the root never receives it. The packed matrix does not exercise a ref.
- **F6: choices where the spec and plan are silent.** A blank or non-string `dateTime` is ignored and the entry still renders as plain text (block 4 invalidates an entry only for a blank label or value); a blank `newTabText`, `messages.tags` or `messages.links` warns even when its list does not render; the warnings fire in the order metadata, tags, links, `newTabText`, `messages.tags`, `messages.links`. Each is tested and none changes a promise.
- **F7: the plan's "182 should not move" is wrong.** `beforeIndicatorConventions(actual)` counts the registry minus the three Indicator conventions, so it moved from 182 to 185 together with the total (185 to 188), as it did when `step-count` joined.
- **F8: the artifact grew by 5,441 bytes and renumbered its utility table.** Two utilities are new in `anatomyUtilities` (`gap-x-8`, `gap-y-3`; 401 to 403), 118 of the old 401 positions move, so 32 pre-existing components differ in raw bytes only through renumbered indices. Resolving every index through its own table shows **zero semantic differences across all 190 pre-existing components** (and none in `types`, `tokens` or `assets`). The real changes are the `DetailHeader` component (191 now), one catalog entry (115), three new naming entries (188) and six existing ones gaining `DetailHeader`.
- **F9: changelog placement and scope.** Both bullets sit at the top of their `### Added` section, newest first as the files state and as the earlier lanes did, not "after the last bullet" as plan section 7 words it. No `effects` or `mcp` changelog entry was written: those files are outside this lane's allowed surfaces and the plan says neither package changes (only the `mcp` README digest was regenerated).
- **F10: the test file and the commit slicing differ from the plan's estimates.** `DetailHeader.test.tsx` is 1,286 lines for 165 tests (the plan said about 470), and the plan's seven slices cannot be reproduced file by file because the suites and the integration files mix concerns; the proposed grouping is six commits (see the report).
- **F11: `pnpm test:package-release` fails only on the two known changelog headings** (`@egdev/tokens: CHANGELOG.md top section is 0.7.0, expected 0.6.1` and `@egdev/cli: CHANGELOG.md top section is 0.5.0, expected 0.4.0`); 13 of 18 pass and the five failures are the same `release:pack` abort. Both clear when the parent folds the versions.
