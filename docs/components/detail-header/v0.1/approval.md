## Amendment 1 — F1: `wrap-anywhere` on the link item recipe (2026-11-27)

The amended payload hash below is the current one. The SHA256 at the top of this record stays as the hash the original approval bound.

- **Date:** 2026-11-27
- **Reason (finding F1):** the real-browser check of the #572 implementation (ODD S4, task T6: Chrome for Testing 153 on the static Storybook build and on bare consumer pages; [implementation-evidence.md](implementation-evidence.md), finding F1) found that an unbroken link label does not wrap. At a 320px viewport (272px content width) a 90-character label with no break opportunity stayed one 785px line inside its 272px item (`li` `scrollWidth` 785 over `clientWidth` 272), because the approved link item recipe `min-w-0` lets the item shrink but gives the label nowhere to break. DH-11 promises that long link labels wrap with no horizontal overflow; the implementation read that as multi-word labels, followed the approved recipe and reported the limit instead of changing it.
- **Change:** the two passages that spell the link item recipe and its wrapping promise, and nothing else in the payload. Block 6, "Proposed utilities": the link item gains the existing static utility `wrap-anywhere` (the value recipe `detailHeaderValueVariants` already carries it), with the reason. DH-11: the promise names unbroken link labels and says in one sentence what stays outside it, and the planned method adds an unbroken-label fixture, with and without a universal border-box reset. Header metadata above the hash anchor records the amendment (status, approval and recovery, and the `approvalReference` and `contentSHA256` identity fields).
  - Before: link item `min-w-0`.
  - After: link item `min-w-0 wrap-anywhere`.
- **Owner approval (verbatim):** "Agregar `wrap-anywhere` (Recomendado)" — the owner's answer to the finding raised by the implementation writer and relayed by the parent (`odd/tasks/round-5-consumer-requests.md` L8, "a small spec and code amendment"). It is recorded as the renewed approval of the amended spec.
- **SHA256 of the spec payload** (same hash definition as above):
  - Old: `df34b603ee5474f6019997d8f367117d2790e212511b538a6c6b289a10988ece`
  - New: `97f8419da9fed153dd3cba8483f9295843edc4e55b113de6d540bade09b851c8`
- **What the utility reaches (measured, Chromium 153):** on the link item, and equally on the DetailHeader root so that every part inherits it, `wrap-anywhere` makes an unbroken link label wrap (3 lines at 320 and 390px, no overflow, with and without a preflight). The cause is the cascade, not the recipe: `overflow-wrap` is inherited, but Chip declares `white-space: nowrap` on itself and Heading declares `overflow-wrap: break-word` on itself, so no class on a DetailHeader-owned part reaches either. Making them wrap needs a change to Chip, Heading or SectionHeader, which plan G8 keeps for the owner.
