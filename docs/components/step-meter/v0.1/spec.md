## 1. Purpose and scope

- **Need / non-goals:** A passive, informative indicator of a **coarse level**: a short row of skewed steps, filled from the inline start and empty afterwards, named in words by the consumer (S1: "High progress"). First consumer: egdev-website's Pulso "now" cards, beside the footer link (consumer issue egdev6/egdev-website#45; request #556; markup `egdev-foundation/reference-web/pulso-source.html:894,903`; CSS at `:205-207`, which the request cites as `:206-208`). Non-goals: not a measurement or percentage; not task progress with a readout; not a rating input or any other control; not a position or navigation marker; no built-in text; no live announcement; no animation; no size, variant or tone axis in v0.1; nothing NowCard-specific (the footer fit belongs to [NowCard v0.3](../../now-card/v0.3/spec.md)).
- **Cataloging decision / alternatives:** **new** atom, owner-approved (L3). The reuse → variant → compose → extract order was walked on inspected public code; each earlier step fails:

| Option | Inspected | Why it does not cover the need |
| --- | --- | --- |
| Reuse **MeterRow** | `packages/ui/src/molecules/meter-row/{types.ts,useMeterRow.ts}`; export `packages/ui/src/index.ts:69` | A column with a hidden header (label, key, readout) over one `lg` ProgressBar. `value` is a continuous 0–100 percentage (decimals kept, non-finite means indeterminate); the visible label and readout are required; "ProgressBar alone owns semantics"; its contract excludes "capacity, quota, CPU load or arbitrary measurements". It is a full row, not a coarse indicator that can sit beside a footer link. |
| Variant of **ProgressBar** (Radix Progress) | `packages/ui/src/atoms/progress-bar/{types.ts,useProgressBar.ts}`; `@radix-ui/react-progress` is installed | Radix Progress owns the `progressbar` role and a numeric percentage; the fill is continuous (`scale-x` driven by the inline `--eg-progress-value`); sizes are a 2px hairline or a 10px Material well. A stepped, skewed, named-image indicator is another responsibility and another ARIA role, so a `steps`/`segments` variant would stop being a variant (`docs/CATALOGACION.md`: "Una variante deja de serlo cuando introduce otra responsabilidad"). |
| Compose **Pixel** | `packages/ui/src/atoms/pixel/{types.ts,usePixel.ts}`; `docs/components/pixel/v0.1/spec.md`; `docs/components/pixel/v0.1/observed/browser-check.md` | (a) Fixed 6.4×9.6px box (`w-2 h-3`) whose parallelogram is about 1:1 (width to thickness); `className` is placement-only and there is no size prop, so the reference's 14×8 step (1.75:1) cannot be reached without reopening Pixel's approved API. - **Evidence / level and package:** Atom in `@egdev/ui`, proposed `packages/ui/src/atoms/step-meter/`. One concept (a coarse stepped level) whose steps are parts of one control; none of the atom disqualifiers in `docs/CATALOGACION.md` applies (no peer concepts, no slots, no collection or navigation, no shared coordination state, no interaction pattern, one documented flow). **Radix base: none.** The installed individual packages under `packages/ui/node_modules/@radix-ui` include no stepped or meter primitive; `react-progress` is the closest and is continuous (rejected above). ## 2. Anatomy and composition

| Part | Responsibility | Native element / Radix primitive | Allowed content |
| --- | --- | --- | --- |
| Root `eg-step-meter` | The single named image that carries the level | `span` with `role="img"` and `aria-label` taken from `label`; no Radix | `steps` step spans and nothing else |
| Step `eg-step-meter__step` | One skewed step, `data-state="filled"` or `"empty"` | empty `span`; no Radix | none: no text, icon or children |

- **Radix / composition:** none. No Surface, no Pixel import, no SVG, no icon, no text node, no `asChild`, no ref. Because `role="img"` makes its children presentational and the steps have no text, there is nothing to hide from assistive technology.
- **Public markers:** `eg-step-meter` is the stable public root marker. `eg-step-meter__step` is a retained internal marker with no part-selector API (Gauge's `eg-gauge-well` precedent). `data-state` on each step is the documented own state; it is styled through data variants, never mirrored into classes, and the legacy `.is-on` class is not used. Legacy `.eg-now-card__meter` rules (`packages/ui/src/styles/legacy/bundle.css:283-285`) stay untouched and select `.eg-now-card__meter>i`, so they cannot match this markup; the plan proves it with the shipped stylesheet.

## 3. Public API

**Prop conventions:** looked up in the [canonical registry](../../../../skills/_shared/prop-naming.json) and [generated view](../../../prop-naming.md) by meaning, name and aliases (no entry has aliases):

| Concept | Result |
| --- | --- |
| Accessible name of the displayed level → `label` | Reuse approved `accessible-name` (`label`: "the accessible name of the control or displayed magnitude"; existing usages Gauge, ProgressBar, MeterRow). Not rendered visibly, as in ProgressBar. Not `valueText`: `measurement-text-equivalent` is the text equivalent of a normalized magnitude and its `avoid` lists "accessible naming". |
| Number of filled steps → `value` | Reuse approved `primary-value` (`value`: "the selected value or displayed measurement; domain and type are component-specific"; avoid: inferring editability, numeric universality or shared normalization). | Total number of steps → `steps` | **No approved entry fits.** `max` is `indicator-count-cap` (avoid: primary numeric bounds), `count` is `indicator-count` (avoid: primary measurements), `items` is `collection-items` (structured entries), `size` is `preset-dimensions` (dimensions), and Slider's `step` is an increment. **New concept proposed:** semantic ID `step-count`, name `steps`, component-specific type `number` (integer 1–10, default 4), status `proposed`, `approval: null`. Proposed meaning: "Total number of discrete steps of a stepped scale." Proposed avoid: item or entry counts, display overflow thresholds, step increments of a continuous control, and wizard or navigation step lists. The usage's `source` does not exist yet (new file); at implementation it records `packages/ui/src/atoms/step-meter/types.ts`, symbol `StepMeterProps` and the whole-file `sha256` of the reviewed source. | Size, variant, tone, state | Not used: v0.1 has no such axis (§6). Inherited native attributes and `className` need no own convention. |

## 4. Behavior

| Input / action | Expected result | Event |
| --- | --- | --- |
| `label="High progress"`, `value={3}` | One `span.eg-step-meter` named "High progress" with four steps: the first three `data-state="filled"`, the last `empty`, in DOM order | none |
| `value` 0, 1, 2, 3, 4 with default `steps` | Exactly `value` leading filled steps, then empty ones; 0 renders four empty steps and stays named | none |
| `value` above `steps` (9) or below 0 | Clamped to all filled or all empty; never throws | none |
| Fractional finite `value` (2.9, 0.9, -0.5) | Floored and clamped: 2, 0, 0, so the level is never overstated | none |
| `value` NaN, ±Infinity or not a number (untyped) | Development warning `StepMeter requires a finite numeric value. Nothing was rendered.` and no output; a later valid rerender renders normally | none |
| `label` empty, whitespace-only or not a string | Development warning `StepMeter requires a non-empty label. Nothing was rendered.` and no output (never an unnamed image) | none |
| `steps` 1–10 | That many steps; `value` clamps against it | none |
| `steps` invalid or out of range (0, -1, 11, 2.5, NaN, Infinity, non-number) | Four steps, silently; `value` clamps against 4 | none |
| `label`, `value` or `steps` changes on rerender | Name and steps update immediately: no transition, animation or announcement | none |
| Pointer, keyboard, focus | Nothing happens: not focusable, no tab stop, no handler reaches the DOM | none |

- **States / representation:** Only the steps carry `data-state` (`filled` or `empty`); the root has none. Each invalid input emits its own warning, behind the same development-only guard NowCard uses (`process.env.NODE_ENV !== 'production'`). The warning strings carry the component name and change if OQ-1 renames it.
- **Limits / consumer responsibilities:** The consumer maps its domain to `value` and to the wording of `label` and keeps them coherent; the component cannot verify that "High progress" matches three of four. Not for measurements, percentages or capacity (use Gauge, ProgressBar or MeterRow). The component never announces a change; a dynamic level needs the consumer's own live mechanism. Dates, copy and layout around it belong to the host.

## 5. Accessibility

- **Accessible name / roles / relationships:** `role="img"` on the root with `aria-label={label}`; the steps are presentational. Semantics were weighed and the first row is proposed (OQ-2):

| Option | Verdict and reason |
| --- | --- |
| `role="img"` + consumer `label` | **Proposed.** Matches S1 and the reference markup (`span role="img" aria-label`). The information is a qualitative level whose name is the consumer's wording, with no numeric claim. Needs no value attributes to keep coherent with the name, is universally available, and leaves the steps presentational. Trade-offs: no machine-readable value, announced as an image or graphic, and the consumer must keep wording and fill coherent. |
| `role="meter"` with `aria-valuenow`, `aria-valuemin`, `aria-valuemax`, `aria-valuetext` | Rejected for v0.1. ARIA requires a numeric value, so a coarse level would be announced as a percentage ("75%") it does not have, and MeterRow's contract rejects "arbitrary measurements". Gauge uses it for true measurements (`useGauge.ts`). Assistive-technology support for `role="meter"` is not verified by this spec. |
| Native `<meter>` | Rejected. Its user-agent internals cannot paint skewed steps, so it would need `appearance: none` plus a second decorative element; its `low`/`high`/`optimum` attributes encode a good-or-bad evaluation that does not apply; and the HTML Standard positions it for scalar measurements, not progress (cited from general knowledge, not re-fetched in this session). |
| `role="progressbar"` (ProgressBar) | Rejected: task-completion semantics, continuous, percentage-based. |
| Decorative (`aria-hidden`) plus visible text | Rejected: S1 asks for an accessible name, and the reference has no visible text. |

  Required consumer input: `label`. Guidance for the wording: it must stand alone when a screen reader reaches it inside the card (for example "High progress", not repeating the card title). The Foundation `NowCard/README.md` shows "Progreso alto: 3 de 4" and the page source "Progreso alto"; both are consumer wording, and a count may be added by the consumer. No default label: the Foundation's `progressLabel` default ("Progreso n de 4") is built-in text, and a built-in English default would need a `messages` dictionary and a localization policy and could contradict the card's own wording.
- **Keyboard / focus:** Not applicable: non-interactive, no tab stop, `tabIndex` protected. The host's link stays the only focus target.
- **Announcements / other conditions:**
  - Announcements: none (static image, no live region). Touch target: Not applicable.
  - **Color independence (normal mode):** filled and empty steps differ in lightness, not hue alone, and in position (the filled run starts at the inline start); the level also exists as text through `label`. Estimated from the documented token values with the sRGB formula (hand-computed, not browser-measured): neon filled step against `surface-0` 4.61:1 (matches the token comment, `packages/tokens/src/theme.css:78`), 4.30:1 against `surface-1`; empty step (brand 22% over `surface-0`) against `surface-0` about 1.2:1 (the token comment calls it decorative, `:128`); filled against empty about 3.9:1 on `surface-0` and 3.6:1 on `surface-1`. Contrast is specified on the NowCard footer band (`surface-0`) first; other hosts need their own proof.
  - **Inherent tension (OQ-5):** with a neon filled step, an empty step that is darker than the neon and visible at 3:1 or more against `surface-0` would need a relative luminance of about 0.12 to 0.215, so it differs from the neon by at most about 1.5:1, a hue-only difference (hand-computed). Only an empty step brighter than the neon (near-white, about 0.75 or more) would restore a 3:1 difference, and that inverts the lit and unlit reading. The reference resolves it by keeping empty steps decorative. The informative graphic is the filled run; WCAG 1.4.11 is not claimed for the empty remainder, and the name carries the level in text.
  - **Forced colors (proposed, OQ-6):** the recoloring by the user agent must not collapse the two states (Pixel's observed check shows its past and active states do, accepted there because Pixel is decorative; StepMeter is informative). Proposal, using system-color keywords only and no new token: under `forced-colors`, filled steps paint `CanvasText` and empty steps are not painted (transparent), with `forced-color-adjust: none` scoped to forced colors, following ColorSwatchGroup (`packages/ui/src/molecules/color-swatch-group/types.ts:91-114`). The distinction is presence versus absence, never hue; the total is not visible in forced colors (as it is nearly invisible in normal mode); the name is unchanged. Cascade between the plain and forced rules is proven by computed style, not by class order. Chromium emulation is the planned evidence; Firefox and real Windows High Contrast themes are Not evaluated unless separately checked.
  - **Reduced motion / transparency:** no motion or transform on any part and values apply immediately; the 22% tint is a color, not a translucent surface, so no solid fallback applies.
  - **Not evaluated:** screen-reader output, zoom and reflow in real browsers, RTL appearance (steps follow the inline direction; the slant is fixed and not mirrored), protan and deutan simulations (the brand neon relies on the same standard-observer contrast as other DS fills).

| Variant axis | Allowed values | Default or rule | Combinations / restrictions |

Rejected: a Surface `well` per step (the clip-path would clip the inset shadow and four wells are noise) and one well behind all steps (a track the reference does not have; the NowCard footer band is already the `surface-0` tone).
  - **Geometry (candidate, OQ-4):** a 27° slant (the reference's `skewY(27deg)`; Pixel's polygon is about 26.9°). This is candidate arithmetic, not a browser measurement; the plan proves emitted CSS and computed geometry in Chromium and stops and returns if they disagree. The scaled meter is visibly smaller than the reference's 14×8 (an allowed difference to adopt, as in Pixel OQ-2).
  - **Candidate utility inventory (proof owed by the plan):** root `eg-step-meter inline-flex flex-none items-center gap-1`; step `eg-step-meter__step inline-block flex-none w-3.5 h-3.75 [clip-path:polygon(0_0,100%_47.6%,100%_100%,0_52.4%)] bg-alpha-red-22 data-[state=filled]:bg-fg-brand-default transition-none`, plus the forced-colors utilities of §5 (`forced-colors:forced-color-adjust-none`, `forced-colors:data-[state=filled]:bg-[color:CanvasText]`, `forced-colors:data-[state=empty]:bg-transparent`).
