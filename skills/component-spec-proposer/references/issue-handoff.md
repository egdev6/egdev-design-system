# Spec-to-issue handoff

Activate only on an explicit request such as “sacar spec a issue”. Prepare a concrete, exact versioned component contract, never an issue whose task is to define that contract. Keep the approved spec → separately approved plan → code sequence; issue creation approves neither plan nor implementation. Save the spec only with permission; never hallucinate approval.

## One component, one issue

The initial issue body contains the first versioned spec. Keep **one issue per component**, not one per version. Later modifications are separately authorized **comments**, not silent body replacements. Each comment contains the full versioned snapshot, or a delta plus an accessible recoverable full snapshot, with reason, compatibility impact, VIS IDs/verified image links, previous snapshot-comment link (initial body for the first follow-up) and exact approval scope. Include version, content SHA-256 (canonical payload excluding tracking metadata), visual hashes, `approvalReference`, `canonicalIssue` and `latestPublishedComment` (Pending until readback); follow the [template](../../_shared/component-spec-template.md). Different component-specific types do not imply different global registry conventions or global approval.

Gauge's initial #30 body is v0.4 per supplied context, not a fresh remote check. Local v0.5 was unpublished; v0.6 is also Draft. The next authorized change must be a **comment on [#30](https://github.com/egdev6/egdev-design-system/issues/30)**, not a body edit or new issue. No remote action is authorized here.

## Readiness and body

- Identify component, spec version, Draft/Approved status, recoverable spec/approval references and pending dependencies/non-goals. Open blocking choices (including the meaningful mandatory stylesheet role) prevent implementation-ready export. Only an explicitly requested draft issue may carry them, prominently **Draft — not ready for implementation**.
- Link the [canonical prop registry](../../_shared/prop-naming.json) and [generated view](../../../docs/prop-naming.md); include exact applied entry IDs/prop mappings, new semantic-ID proposals, component-specific types and manually reviewed `source: {path, symbol, revision}` (`sha256:<whole-file byte hash>`). Carry exception component `scope`, alternative `propName`, `reason` and pending/approved evidence. Convention approval requires recoverable `{reference, scope, contentHash}` bound to `convention:<id>`; exception approval binds `exception:<id>:<scope>:<propName>` and its semantic hash. Follow the [shared lookup workflow](../../_shared/component-contract.md#prop-naming-registry) and canonicalization rules in the generated view. Never copy the global matrix, invent approvals, silently refresh stale evidence or promote convention status from component/issue approval; local validation does not prove consent or TypeScript correctness.
- Include all seven spec blocks: purpose/scope; complete anatomy/composition; complete API types, requiredness/defaults, native props/refs and exports; behavior/states/limits; accessibility roles, names, keyboard, focus and announcements; Material/token/utility contract and all seven meaningful file roles; acceptance criteria.
- Preserve compatibility/public exports/classes, per-part className/merge limits, provenance and explicit approval status. Include expected-design VIS IDs, real images, source/version, capture conditions and recoverable human approval. Record uncertainty, never substitute current implementation for approved design.
- Provide story and test matrices covering applicable variants/states, behavior, accessibility, composition, merge invariants, CSS build/static CVA scanning and a package consumer without a Tailwind compiler. Map each promise to an acceptance ID, method and evidence; distinguish planned checks from actual results.
- Local images are not GitHub-visible. Follow the [concrete asset handoff](../../../docs/design/README.md#github-visible-image-handoff): choose human attachment or bounded authorized asset-publication branch; verify the actual URL's accessibility and PNG hash before linking. Use English alt text/metadata; no fake URLs, local/tmp paths, guessed `gh` upload commands or implied commit/push/upload permission. Missing authorization/tooling or inaccessible images blocks visual handoff, not grounds to fabricate success.

## Authorized workflow boundary

1. Return the exact English initial body or subsequent comment for review, with snapshot identity, readiness, blockers and verified image accessibility. Ask explicitly for **create-issue handoff** or **add-comment handoff** on the exact existing issue. Preparation authorizes no remote reads/writes.
2. Delegate publication guidance to the global `gentle-ai-issue-creation` skill and its `references/delegated-workflow-actions.md`; do not edit them or invent a local substitute. Require exact host/repository, existing issue number for comments, requested discovery/action and credential/session authorization **before any remote access**. If unavailable or ambiguous, stop locally. Creation follows repository forms, duplicate search and reviewed field mapping; a later version uses the confirmed canonical issue.
3. Review the exact body/comment and privacy immediately before the single authorized action. Freshly read the target/history for concurrency, preserve human comments, body, states and labels, and stop on conflict. No silent body edits, label/status changes, closure or additional writes; each would require its own direct authorization.
4. Perform one bounded write only after exact action/content approval, then read back the target-host issue/comment and verify content/identity. Record the actual comment URL only after matching readback. Ambiguous responses require STOP/reconciliation, never blind retries or duplicate issues/comments. Publication does not grant approval or authorize a later action.

Return the reviewed body/version, readiness and unresolved choices, image accessibility, intended destination/operation and authorization state; after an authorized handoff, report only observed write/readback evidence, never invented success.
